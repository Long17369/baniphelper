- **阶段三 S3.3 事件订阅已落地**（见 [phases/03-observation.md](phases/03-observation.md) 第 3.2 与 3.3 节）：
  订的是 `Microsoft-Windows-Kernel-Network` 的 **TCP 生命周期事件**，按事件号在**内核侧**过滤，
  因此不再轮询、也不再收每报文一条的数据事件。声明了 `EventDrivenConnections`，两个后端都订得上
  （内存后端真的把投进去的事件送到订阅者手上，用来验「订上了就真收得到」）。
  五个要单独记住的结论：
  - ⚠️ **`saddr` 在两种协议下指的不是同一端**：TCP 的全部事件里它**恒为本端**
    （收包事件也一样），而 UDP 的**收包**事件里它是**对端**。按错的解释走不会报错，
    只会让所有接收方向的对端变成自己
  - 朝向是靠**两端端口都已知的回环连接**量出来的，不是读文档推的；IPv4 与 IPv6 各自验过
  - **把「连接尝试」当成出现**是有意的（出站方向只有这一个事件），失败与关闭算消失；
    同一个连接只报一次出现，关闭不设门口
  - ⚠️ **未提权时 `StartTraceW` 会成功**，拒绝发生在 `EnableTraceEx2`（权限检查在启用
    系统提供程序那一步）—— 只查第一处会把「请以管理员身份运行」写成一句平台错误
  - **UDP 的数据报事件不进这条通道**（逐报文会把记录表打爆），逐包数据留给 S3.4；
    另外 TCPv6 没有「尝试失败」事件，失败的 v6 尝试会留下一条记录等关闭或保留期清理
- **阶段三 S3.2 TCP 流量统计已落地**（见 [phases/03-observation.md](phases/03-observation.md) 第 3.4 节）：

  - ⚠️ **未启用采集就读会「成功」并返回未初始化内存里的垃圾值**（不是 0、也不报错）。
    所以 `read` 之前必须自己记账「启用过没有」，把这件事交给 API 就会把垃圾当流量显示出去
  - ⭐ **计数覆盖整条连接**（回环上传 100 KB 后才启用，读出来正好 102400；
    关采集期间传的 20 KB 事后也在计数里）→ 原先设想的「自启用起计数」是**错的**。
    而连接建立时刻平台给不出来，`since` 只能填保守下限，界面不许写「自此刻起计数」
  - **批量读不整体失败**：拿不到计数的条目用**空 `since`**表示；单条 `read` 则明确报「找不到」
  - 实测口径：回环上传 100 KB 后启用读到正好 102400、再传 50 KB 增量正好 51200，
    两侧方向互为镜像，别人的连接也能启用与读取，只给四元组就够（不需要状态位）
- **S2.3 的范围需要重新界定**：原先写的是「可执行文件路径到设备路径的转换」，
  而那件事在 S2.4 里由系统的 `FwpmGetAppIdFromFileName0` 解决了 ——
  自己拼 NT 设备路径本来就是把卷映射规则抄一遍，抄错了规则会落到别的程序上，
  而且不报错。`ITargetResolver` 剩下的价值是「进程存活跟随」，
  等 S3 要按进程归组连接记录时再动。
- 阶段划分为 S1 到 S8，步骤编号已稳定，新增只追加、作废不删除
- 与机器相关的信息（工具链绝对路径、版本号、命令）由开发者自行记录，未入库

| 决策 | 结论 |
| --- | --- |
| 形态 | 提权托盘单进程，不做服务 |

### 6.2 文档格式

- 项目文档使用**中文**
- 每次改完文档跑一次 markdownlint（`markdownlint-cli2`），**要求 0 错误**
- 已放宽的规则只有 MD013 行宽一项，理由是中文排版；其余规则一律靠正文合规满足
- 常见坑：表格分隔行要写 `| --- |` 且带空格；代码围栏必须带语言；标题、列表、表格、围栏前后都要空行；不要用独立成行的粗体当标题；同一文件内标题不能重复

### 6.3 并行编辑的教训

**同一文件的多次编辑必须串行提交。**
规划期曾并行提交五处编辑，结果段落互相插入、内容错乱，修了两轮才恢复干净。

### 6.4 代码风格与工程约定

| 项 | 约定 |
| --- | --- |
| 语言标准 | C++17，关闭编译器扩展 |
| 命名 | 类型用大驼峰，函数与方法用小驼峰，变量用小驼峰，私有成员尾随下划线 |
| 命名空间 | 一律落在 `baniphelper` 之下，再按层分 `core` 等子命名空间 |
| 包含路径 | 以 `src/` 为包含根，写成 `core/xxx.h` 与 `platform/api/xxx.h`，让依赖层次在 include 语句里直接可见 |
| 格式化 | 根目录 `.clang-format`，基线 Google（同行花括号、2 空格缩进），只保留四项刻意偏离，理由写在文件内；改完代码跑一次 clang-format |
| 文件编码 | 一律 UTF-8 **无 BOM**。`.clang-format` 带 BOM 会让 clang-format 解析失败并静默回退到默认风格 |
| 编辑器设置 | 格式化出口固定在 `clangFormat`，见 `.vscode/settings.json`；若用 `vcFormat` 会完全绕过 `.clang-format`，且它默认缩进命名空间内容 |
| 注释 | 中文；解释「为什么」而不是复述「做什么」；接口头文件必须写明语义与不变量 |
| 平台隔离 | `core/`、`platform/api/`、`ui/` 与 `tests/` 不得引用平台专有头，由构建期两道检查强制。平台差异只能出现在 `platform/<os>/` 下 |
| 测试 | 一律用 CTest 注册，跑 `ctest --preset debug`，不要另建一套私有命令 |
| 构建 | 一律走 CMake 预设，不手写底层 cmake 命令；命令行构建所需的环境变量由开发者自行记录（未入库） |
| 工具链 | 只允许 Qt 套件自带的 MinGW，混用另一套会被顶层 `CMakeLists.txt` 直接拦下 |
| 依赖部署 | 构建后由 `windeployqt` 把 Qt 运行库放到可执行文件旁边。这是必需的，不是优化：提权启动不继承终端的 PATH |
| 界面子系统 | 界面可执行文件必须设 `WIN32_EXECUTABLE`，否则双击会多带一个控制台黑框 |

## 7 开发环境推荐

### 7.1 写代码与调试

首选 **Qt Creator**（随 Qt 安装）：原生支持 CMake 与 Qt 自带的 MinGW，调试器集成好，
并且能直接以管理员身份启动被调试进程，这对提权托盘程序很关键。
VS Code 加 CMake 与 C++ 扩展也可用，但提权调试更麻烦。

### 7.2 命令行 shell

按用途分三档，不要用一个 shell 硬扛所有事：

| shell | 适合 | 不适合 |
| --- | --- | --- |
| Git Bash | 日常命令、构建脚本、需要可移植的脚本 | 调用 Windows 专有工具时路径转换易出错 |
| CMD | Windows 专有工具（`wevtutil`、`netsh` 等）与一次性命令 | 复杂脚本 |
| PowerShell | 需要 .NET 或 PS 模块时 | 作为默认脚本环境 |

PowerShell 的具体坑，以下均为本项目规划期实测踩到过的：

1. 多行命令粘贴常被当成多段执行，或卡在续行状态，需拆成单行或写进脚本文件
2. here-string 管道给外部程序不可靠
3. 双引号里的变量会被提前展开，传给外部程序时容易变成空值
4. `>` 重定向默认写 UTF-16，别的工具读会看到空字符
5. `&&` 不可用，只能用 `;`，而 `;` 不保证前一条成功

结论：**构建与脚本用 Git Bash，Windows 专有工具用 CMD，只有必须调 PowerShell 模块时才用它**。
若坚持用 PowerShell 做主环境，务必把命令写进脚本文件再执行，不要粘贴多行命令。

## 8 已知的坑

| 坑 | 说明 |
| --- | --- |
| 同一文件并行编辑 | 见 6.3，必须串行 |
| 格式化配置不生效 | 见 6.4：先确认编辑器用的是 `clangFormat` 而不是 `vcFormat`，再确认 `.clang-format` 无 BOM |
| 提权启动找不到 Qt 运行库 | 见 6.4 的依赖部署：提权进程用的是用户注册表里的环境，不继承终端的 PATH |
| 双击后多出一个黑框 | 见 6.4 的界面子系统：控制台子系统会把控制台窗口一起带出来 |
| 提权实例停不掉 | 普通权限的 `taskkill` 对提权进程返回「拒绝访问」，要用 `sudo` 起一个提权命令去停 |
| 链接时 exe 写不进去 | 上一个实例还开着，exe 被占用。先结束实例再构建（这也是发布前要处理的现实问题） |
| WFP 枚举过滤器必须给层 | 枚举模板只给 provider 会被 `FWP_E_LAYER_NOT_FOUND`（`0x80320004`）拒绝，得逐层枚举 |
| WFP 层 GUID 要自己维护 | 工具链的 WFP 头不含 `FWPM_LAYER_*`，写错会静默落在别的层上；校验办法见 [architecture.md](architecture.md) 第 10 节 |
| WFP 对象会持久存在 | provider 与 sublayer 用非动态会话注册后会一直留在系统里（这是刻意的：它们是身份不是规则）。所以 `netsh wfp show filters` 的 XML 里能查到自家 provider 条目，别把它当成残留过滤器 |
| 核心层里平台头突然找不到了 | 那是受约束目录里的**预期行为**，见 6.4。确实要调系统接口，就把它放到 `platform/<os>/` 下，不要想办法绕过检查 |
| 提权进程调试 | 普通权限调试器无法附加，需以管理员身份启动调试器 |
| 退出后过滤器残留 | 过滤器在进程退出后仍在内核存活，启动清理必须有 |
| 托盘上找不到退出入口 | 关窗只是收进托盘，退出在托盘右键菜单里。托盘**不可用**时程序会改成「关窗即退出」，不允许出现既没图标又没窗口的进程 |
| 给提权窗口发消息 | 普通权限进程发的 `WM_CLOSE` 会被 UIPI 丢掉，验证关窗行为要用 `sudo` 起脚本 |
| 命名管道上的假失败 | `ConnectNamedPipe` 返回 `ERROR_NO_DATA`（232）表示「客户端已连上又立刻关了」，**算成功**；此时 `ReadFile` 仍读得到数据。当成失败处理会丢掉整次唤起请求 |
| 两个进程写同一份日志 | `QFile` 的追加在 Windows 上不原子，两个进程各记住的写入位置会撞在一起、互相覆盖一整行。所以单实例判定排在日志之前：抢不到所有权的那次启动是唤醒器，它不写日志 |
| 崩溃后过滤器还在生效 | 未处理异常在本机会被 Windows 错误报告接管，进程在那段时间里**仍然活着**、WFP 引擎会话也还开着，规则照旧执行。所以「崩了就等于网络恢复」是不成立的，界面文案里要说明 |
| 用异常做自动演练 | 本机做不到：`DebugBreakProcess` 之后进程 30 秒仍在（`DontShowUI` 设成 1 也一样）。要演练「不走收尾」，就用内核终止并带上崩溃式退出码，别在异常上耗时间 |
| PowerShell 里的 16 进制常量 | `0xC0000005` 会被解析成**负的 Int32**，强转 `[uint32]` 直接抛异常。P/Invoke 该用 `int` 接的地方就用 `int`；验证脚本里更要紧的是**给关键步骤加断言**（终止之后确认进程真的没了），否则脚本静默失败会产出一份看起来对的错误记录 |
| 清理误伤他方 | 只按自有 provider 与 sublayer 判断归属，绝不按层全量清理 |
| 白名单模式锁死自己 | 超时自动回滚不可关闭 |
| 断连后立刻重连 | 必须保证先封后断，否则对端会在被断的瞬间重连成功 |
