# 阶段一 工程骨架与运行基座

## 1 目标与范围

产出一个「什么都能装、什么都还没做」的程序：能提权启动、单实例、能读写配置与数据库、
能记录日志、能干净退出，并且 WFP 引擎可以安全地打开与关闭。

本阶段**不实现任何封禁逻辑**，只把地基与接口定死。

## 2 前置条件

| 项 | 状态 |
| --- | --- |
| Qt 套件 | 已就绪，含 Qt Quick、Quick Controls、Svg、Charts |
| 编译器与构建 | Qt 套件自带的 MinGW 与 CMake、Ninja 均可用 |
| 绝对路径 | 见环境文档（`tmp/` 下，不入库） |
| WFP 头文件与导入库 | 已核实齐全，无需 Windows SDK |

### 3.1 追加步骤的原因

S1.12 到 S1.16 是实施过程中按[变更控制](../README.md#6-变更控制)追加的步骤，
不是原计划的一部分。它们都不是随手加的功能，而是前一步逼出来的前提：

- **S1.12 与 S1.13** 来自项目自己定的硬顺序（[README.md](../README.md) 第 8.1 节）：
  只要开始写第一个平台实现，就必须同时补内存实现与契约测试。而 S1.3 的验收里
  「二次启动不产生第二个实例」要求界面层拿得到平台实现，于是装配点也不得不先有。
  两者分别是阶段八 S8.1 与 S8.2 的最小版本，完整形态仍留在阶段八。
- **S1.14** 是实施提权清单时暴露的：程序一旦带 `requireAdministrator`，
  经 UAC 提权启动时 Windows 使用的是用户注册表里的环境，
  **不继承开发终端临时加进 PATH 的 Qt 目录**，加载器找不到 `Qt6Gui.dll`，
  程序在 `main` 之前就失败，现象与代码错误完全不像。因此依赖必须放在可执行文件旁边。
- **S1.15** 是实施 S1.7 之后补的。S1.7 靠「运行时枚举全部层」绕开了
  「MinGW 的 `fwpmu.h` 不含层 GUID 常量」这个缺口，但那条路只解决**清理**，
  解决不了**下发** —— 建过滤器必须给出具体的层 GUID。
  与其等到 S2.4 边写边猜，不如先把取值、出处、校验手段和防抄错的编译期断言一次立好。
  代价很小（一张常量表加一个核对工具），买到的是
  「S2 的规则不会因为一个抄错的 GUID 而静默失效」。
- **S1.16** 是实施 S1.8 时暴露的接口缺口。S1.3 冻结 `ISingleInstance` 时只写了
  「取得所有权」「唤起既有实例」「释放」三件事，接收端一直没有入口，
  于是 S1.3 留下了一句「唤起既有实例尚未实现」。
  托盘外壳要当接收端，而接收端必须在 `platform/` 里（命名管道是平台专有的），
  接口没有这个入口就绕不过去 —— 要么改接口，要么让界面层直接包含平台头，
  后者违反四条铁律里的第一条。按[变更控制](../README.md#6-变更控制)：
  第 3.2 节的冻结清单已同步更新，阶段八的契约测试清单也加了一条。

### 3.2 实施 S1.4 时对验收口径的调整

S1.4 原定的验收是「日志可滚动且不会无限增长」，手段写的是「单文件滚动与**总量上限**」。
实施时改成了**按时间保留 + 滚动后压缩**，不设总量上限：

- 滚动：单文件 **4 MB** 滚动
- 压缩：滚动后立刻用 zlib 压缩，产物是 `<主干>-<时间戳>.log.z`
- 保留：只留最近 **7 天**，按文件修改时间判断
- 不设总量上限：纯文本压缩后大致只剩十分之一，一周的量通常只有几 MB

之所以改，是因为原方案那个总量上限的数字只能靠猜：设小了会在日志最有用的时候
把历史删掉，设大了等于没设。按时间保留的语义对使用者更直白 —— 「能回看一周」。

**残留风险**：若日志量异常放大（例如某个循环里反复写日志），一周内仍可能吃掉可观磁盘。
缓解手段不是再加一道上限，而是不让它异常放大：级别默认只到 `Info`，
`Debug` 必须显式打开，而写日志的调用点也应该是有意义的动作，不是循环内的流水账。

### 3.3 S1.4 顺带补齐的前置：路径实现

`Paths` 结构体在 S1.2 就冻结了，里面**已经预留了 `logDirectory` 字段**，
但 `IPaths` 一直没有任何实现，装配点里也没有 `paths` 成员。

日志必须知道往哪写，而 `core/` 与 `ui/` 都被平台隔离检查挡着、不能直接问系统要路径，
所以这一步绕不过去。顺带补上：

- `WinPaths`：落在 `%APPDATA%\BanIPHelper` 之下，先问系统（`SHGetFolderPathW`）
  再退回环境变量；不用更新的 `SHGetKnownFolderPath`，因为 MinGW 不给 `FOLDERID_*` 的
  GUID 定义，为一个目录路径多挂一个库不划算
- `MemoryPaths`：落在系统临时目录下，刻意**不碰用户真实配置目录**，
  否则跑一次测试就污染开发者环境，两个后端的行为差异也会被掩盖

两者都遵守 `IPaths` 的既有契约：`resolve` 只回答「默认在哪」，
`ensureDirectories` 负责创建并能在目录被删掉后重建。
它同时是 S1.5 与 S1.6 的前置，那两步可以直接用。

### 3.4 实施 S1.5 时的三个决定

**其一：描述符表只放真被消费的项。**

`architecture.md` 第 7.2 节列了全部规划中的配置，但其中多数所属的功能还没做
（`webui.*` 属 S6、`whitelist_*` 属 S4、`record_*` 属 S3）。S1.5 只把**日志组**放进表里
（`log.level`、`log.rotate_bytes`、`log.retention_days`、`log.compress_rotated`），
因为只有这一组现在真被 `main` 读走、并影响实际行为。

理由与能力声明是同一条：一个能被设置却什么也不影响的开关，比没有这个开关更糟 ——
用户会以为改动生效了。其余各项随其功能落地时再加。

**其二：配置键统一加命名空间前缀。**

第 7.2 节的键名不带前缀（`listen_port`、`record_retention_days`），
而冻结的 `ConfigDescriptor` 注释给的例子是 `webui.listen_port`。S1.5 采用带前缀的形式：
表里已经同时存在两个「保留天数」（`log.retention_days` 与规划中的 `record_retention_days`），
不加前缀迟早混淆。第 7.2 节的键名相应改为带前缀。

**其三：交付了一个已知的接口缺口。**

`IConfig::setValue` 没有「来源」参数，而 `ConfigChange::origin` 存在的意义正是区分
`ui` / `webui` / `core` / `import`。也就是说**接口声明了要审计来源，却没有给出传入来源的途径**。

S1.5 的做法是先用具体类的扩展方法 `JsonConfig::setOrigin()` 顶着，
并在阶段六 S6.4（配置接口）开工前解决：要么在接口上加参数，要么约定「来源随调用上下文」。
按变更控制，接口一旦改动要同步更新第 3.2 节的冻结清单。

**另外两条自愈路径都不静默处理**：文件内容不是合法 JSON 时，原文件改名为
`config.json.bad-<时间戳>` 保留后重建；文件里有未知键时忽略但记账。
两者都通过 `recoveryNotes()` 上报，`main` 把它们写进日志。
丢掉用户设置、或悄悄忽略未知键，都会变成事后查不出原因的怪现象。

### 3.5 实施 S1.6 时的四个决定

**其一：只立基础设施，业务表留给各自的阶段。**

S1.6 交付的是建库、WAL、迁移框架与批量写入，加上一张 `meta` 键值表。
`rules` 表属 S2.9、`connection_records` 表属 S3，各自作为**新的迁移**加进来
（代码里已标注位置）。迁移机制存在的意义就是这个 ——
给还没定的表结构提前定型，只会换来一次用不上的迁移。

迁移版本号记在 `meta` 表的 `schema_version` 键里，不单独建版本表：
一张表能同时承担版本号与「本库创建于何时」，比两张只写一行的表好管。

**其二：WAL 必须读回确认，不能执行完就当成功。**

SQLite 在开不成 WAL 时**不报错**，而是返回当前模式（网络盘、部分云同步目录
只支持 delete 模式）。所以 `open` 会把 `PRAGMA journal_mode=WAL` 的结果读回来比对，
不是 `wal` 就直接失败，并提示换成本地目录。

实测佐证：真实运行后 `%APPDATA%\BanIPHelper\` 下同时出现 `baniphelper.db`、
`baniphelper.db-wal`、`baniphelper.db-shm` 三个文件。

**其三：迁移只前进，且每个迁移一个事务。**

库里的版本号高于本程序支持的版本时**直接拒绝打开**，不尝试降级 ——
用旧代码去动新库，比打不开危险得多。每个迁移包在自己的事务里，
中途失败整体回滚：测试里专门造了一条「前半句能跑、后半句是垃圾」的迁移，
验证它建出的半成品表不会留在库里。

**其四：批量写入的三条硬约束。**

- 一个批次只用一个事务。记录量很大，每条一次事务会把磁盘拖垮。
- **绑定个数不一致时整批拒绝**。不一致时 SQLite 会沿用上一行留下的绑定值，
  于是写出「插入成功但值是上一行的」记录 —— 这比报错难查得多，因为库里看起来有数据。
- 任何一行失败都整体回滚，不留「写了一半」的表。

实现上另有一处需要说明：连接锁用的是**递归锁**（`QRecursiveMutex`）。
公开方法之间是互相调用的（`open` 要走迁移、迁移要执行语句、`insertMany` 要开事务），
普通互斥体会当场自锁。换成「内部方法统统加 Locked 后缀」也能解决，
但那把「记得别加锁」变成一条靠人守的纪律，而这里只有一处调用者。

**新增依赖与一个已知取舍**：核心层现在依赖 `Qt6::Sql`（以 PUBLIC 方式传递出去）。
Qt 自带的 `QSQLITE` 驱动把 sqlite3 静态编在插件里，所以不需要额外的第三方库，
也不需要单独分发 sqlite3.dll；`windeployqt` 会把 `sqldrivers/qsqlite.dll` 一起部署
（已实测存在于构建树中）。

**取舍**：数据库随配置和日志一起放在漫游目录 `%APPDATA%\BanIPHelper` 下，
这是 S1.4 定路径时的延续。副作用是 WAL 的 `-wal` 与 `-shm` 边文件会参与漫游同步，
而同步过程可能打断它们。真要解决，得把数据库与日志挪到 `%LOCALAPPDATA%`——
那是一次路径语义的调整，留到有实际反馈时再做，不在本步顺手改。

### 3.6 实施 S1.8 时的五个决定

**其一：托盘用 Widgets 的 `QSystemTrayIcon`，界面入口随之换成 `QApplication`。**

没有走 QML 侧的 `Qt.labs.platform.SystemTrayIcon`：那个模块官方声明 API 可能随时变，
而托盘是这个程序**唯一的退出入口**，把退出入口建在一个实验性模块上不合适。
改用 `QSystemTrayIcon` 的代价是 `ui` 多链一个 `Qt6::Widgets`（`architecture.md`
第 1.3 节本来就写着「Widgets 做托盘与辅助」），以及入口从 `QGuiApplication`
换成 `QApplication`。界面主体仍是 Qt Quick，这一点没变。

**其二：关窗与退出是两件事，而且四条硬约束不许破。**

- 关闭窗口=**收进托盘**，只有托盘菜单里的「退出」才结束进程；
- **托盘不可用时关窗就是退出**。不允许出现「没有托盘图标、窗口也不见了」的进程 ——
  那只能去任务管理器杀，而杀进程不会走撤销过滤器的路径，正好是最坏的结果；
- 第一次收进托盘时弹一次气泡，明确告诉用户程序还在、右键能退出。
  每次收进都弹就成了骚扰，所以只弹一次；
- 退出收尾挂在 `aboutToQuit` 上，而不是挂在「托盘菜单点了退出」上。
  事件循环结束的方式不止一种（菜单、关窗、QML 加载失败后的 `exit`），
  挂在这个信号上才能保证收尾一定发生且只发生一次。

收尾顺序是「撤销 → 关引擎 → 停接收端 → 释放单实例 → 写日志 → 关日志」，
每一步失败都只记录不中断。顺序里有一处必须解释：**先停接收端再放所有权**。
反过来的话，新实例可能在中间那一刻连进来却没人应答，它按契约报「唤起失败」然后退出，
而这边正好也退了 —— 结果两个都没了。

**其三：接收端放进 `ISingleInstance`，它的实现有两处坑。**

接口变更按第 3.1 节的 S1.16 走流程。实现上有两处是实测撞出来才改对的：

- **返回成功时通道必须已经建好。** 第一版把「建管道」也交给监听线程做，
  结果是 `listenForActivation` 刚返回、紧接着的二次启动就撞在「线程还没来得及建管道」
  的窗口上，报出一个假的「既有实例没有在监听唤起通道」。改成在调用者线程上同步建好
  第一个实例、再交给线程接手，竞态就不存在了。
- **`ConnectNamedPipe` 返回 `ERROR_NO_DATA`（232）算成功，不算失败。**
  我们自己的客户端就是「连上、写一句、立刻关」，服务端晚一步调 `ConnectNamedPipe`
  就会看到这个错误码。它字面意思是「没有数据」，很容易被当成失败把这一轮请求丢掉；
  实测此时 `ReadFile` 仍然读得到那 4 个字节。这一条写进了实现注释，别删。

监听线程的等待一律用「停止事件 + 重叠 I/O 完成事件」两个句柄一起等，
不靠关闭句柄去打断阻塞调用 —— 那种做法依赖未文档化的行为，是这类实现最常见的挂死点。

**其四：单实例判定挪到写日志之前。**

实测：两个进程往同一份日志里写，会互相覆盖掉对方的一整行。
原因是 `QFile` 的追加在 Windows 上并不原子，两个进程各自记住的写入位置撞在了一起。

修法不是在日志里加锁，而是承认一件事：**抢不到所有权的那次启动不是第二个实例，
它是一个唤醒器**，职责只有一句「请既有实例把界面拿出来」，然后退出。
它本来就不该往主人的日志里写东西。于是单实例判定排到日志之前，
`main` 的启动顺序从「日志最先」变成「单实例最先」，其余不变。

代价：这一段的失败只能用 stderr 报（日志还没起来），而且唤醒失败时用户什么也看不到。
后者用一次 `QMessageBox` 补上 —— 程序是 GUI 子系统、没有控制台，
「双击了但什么都没发生」正是这个功能要消灭的现象，不能让它以另一种形式回来。
`showWindow` 因此把「主界面已显示」记成 `Info`：唤醒器自己不写日志，
这一行就是「双击到底有没有效」的唯一证据。

**其五：退出即撤销开关进配置表，托盘菜单勾选项与它同步。**

键名按 S1.5 定的规则带命名空间前缀，`architecture.md` 第 7.2 节里的 `revoke_on_exit`
相应改为 `shutdown.revoke_on_exit`。菜单勾选状态在建立菜单时从配置读一次，
用户改动时写回配置；**写失败要把勾退回去**，否则界面显示「已关」而退出时仍然会撤销。
退出时读这个开关用「撤销」作为兜底值：撤销是回到原状，属于安全的那一侧，
反过来默认「保留」的话，一次读取失败就会把用户的网络继续封着。

### 3.7 实施 S1.9 时的演练与两个发现

S1.9 要回答的问题是：**进程没有走收尾就消失时，过滤器会不会一直留在内核里**。
答案是「会」，这不是缺陷而是 WFP 的性质，所以真正要验证的是**下次启动一定会收干净**。

演练做法（脚本在 `tmp/`，不入库）：每种终止方式都先播一条挂在自家 provider 下的过滤器
（规则下发属 S2.4，程序自己产生不了残留），再按对应方式终止进程，最后重启数一遍。
数数用的是 `netsh wfp show filters` 的 XML，**只数带 `<filterKey>` 的条目**
（里面还有 providers 与 sublayers 段，条目同样叫 `<item>`，一起数会多算）。

| 场景 | 终止方式 | 退出码 | 终止后自家过滤器 | 重启后自家过滤器 |
| --- | --- | --- | --- | --- |
| 一 正常退出 | 事件循环结束（等价于托盘菜单退出） | 0 | 0 | 0 |
| 二 强杀 | `TerminateProcess` | -1 | 1（残留） | 0 |
| 三 模拟崩溃 | `TerminateProcess` + 崩溃式退出码 `0xC0000005` | -1073741819 | 1（残留） | 0 |

三个场景的重启都留下了同一条日志：「已清掉 1 条上次运行残留的过滤器」。
结论：**三种情况重启后均无残留**，S1.9 的验收达成。

**发现一：真实的未处理异常在本机没法自动演练。**

原本打算用 `DebugBreakProcess` 在目标进程里制造一次未处理异常，实测不行：
它返回成功，但进程 30 秒后仍在运行（`Responding` 为真、CPU 仍在走），
说明异常被 Windows 错误报告接管了。把 `HKCU\...\Windows Error Reporting\DontShowUI` 设成 1
也照样如此（该值用完已还原）。探针脚本单独放在 `tmp/wer-probe.ps1`，
刻意不混进主演练 —— 它会把进程留在「被 WER 接管」的中间态，混进去后面的结论就说不清。

因此场景三如实记为**模拟**崩溃：用内核直接终止并带上崩溃式退出码。
对「有没有跑收尾代码」这件事，它与真实崩溃等价；真正属于真崩溃的那部分行为见发现二。

**发现二：崩溃之后，过滤器会继续生效一段时间。**

接上一条：进程崩了不等于它下发的过滤器立刻失效。WER 接管期间进程还活着，
WFP 引擎会话也就还开着，规则照旧执行。也就是说**崩溃后的那几秒到几十秒里，
用户看到的网络封锁不会消失**。这不是代码问题，是这条路本身的样子，
但要写进界面文案里（阶段五 S5 的「出事了怎么办」），不能让人以为关掉程序就一定恢复网络。

**脚本自己也要有断言。** 这一轮演练里踩到一个值得记的坑：场景三第一次跑完，
报告显示「崩溃后自家过滤器 = 1、重启后 = 1」，看起来像启动清理失了手。
实际原因是脚本里 `[uint32]0xC0000005` 在 PowerShell 里先被解析成负的 `Int32`，
强转抛异常，`TerminateProcess` 根本没被调用 —— 进程一直活着，于是「重启」那次
其实撞上了单实例，第二份实例自己退了，前一份自然什么也没清。
两个修法都补上了：脚本每步开始前断言场上没有别的实例，终止之后断言进程确实消失，
不成立就把结论标成无效。**结论不可信时宁可说无效，也不要写一条看起来对的记录。**

## 5 阶段验收

八项验收**已逐条实测**（2026-09-22），里程碑 M1「空壳可用」达成。

| # | 验收项 | 证据 |
| --- | --- | --- |
| 1 | 双击启动会请求提权，且启动后确实具备管理员权限 | 清单声明 `requireAdministrator`；判据是 `TokenElevation`，不是「是否属于管理员组」（S1.3） |
| 2 | 二次启动不产生第二个实例，而是唤起既有托盘 | 第二个进程退出码 0，既有实例日志出现「主界面已显示」且窗口回到可见（S1.8） |
| 3 | 配置文件与数据库可自动创建、可读写、可重建 | 删掉配置文件会按默认值重建、改 `log.level` 立刻生效（S1.5）；删掉库文件后启动会建库并打印迁移动作、二次启动迁移只发生一次（S1.6） |
| 4 | 启动时能清理上一次残留的自家 filter，且不会误删其他工具的 filter | 播一条真残留再启动，日志出现「已清掉 1 条」，系统过滤器总数回到基线；归属判据只有自有 provider，他方 filter 在结构上就选不出来（S1.7、S1.9） |
| 5 | 正常退出、强杀、崩溃重启三种情况均无残留 filter | 见第 3.7 节的演练表：三种情况重启后自家条数都是 0 |
| 6 | 全程日志可查，且日志文件不会无限增长 | 4 MB 滚动、滚动后压缩、只留最近 7 天三件套（S1.4） |
| 7 | 核心层与界面层均不引用任何平台专有头，违反时构建直接失败 | 编译期占位头加源码扫描两道检查，故意在核心层引入 `windows.h` 会当场失败（S1.10） |
| 8 | 能力协商可查询，且不存在静默失败的能力路径 | 测试里的覆盖检查守住「新增能力位与错误码必须补文案」（S1.11） |

第 5 项里有一处要说清楚：**强杀与崩溃之后留下过滤器是必然的，不是缺陷** ——
WFP 过滤器不随进程消失。被验收的其实是「下一次启动一定收干净」。

## 6 风险与对策

| 风险 | 对策 |
| --- | --- |
| 提权进程难以被调试器附加 | 日志成为主要排查手段，因此 S1.4 的优先级要提前 |
| 清理孤儿 filter 时误删他方 filter | 只以自有的 provider 与 sublayer 作为归属判据，绝不全量清理 |
| 接口冻结不彻底，后续被迫改动 | S1.2 的验收标准是「实现可以没有，签名与语义必须无歧义」，必要时先写用例再定签名；已经发生过一次（S1.16 给 `ISingleInstance` 加接收端），处理方式是走变更控制：更新冻结清单、在两个后端与契约测试同步补齐，**不就地改** |
| 平台抽象层被绕过，导致后期无法移植 | S1.10 的构建期检查是硬约束，代码评审时对核心层出现平台概念一律打回 |
