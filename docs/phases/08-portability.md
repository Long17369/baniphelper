# 阶段八 跨平台后端

## 1 目标与范围

把平台相关实现替换为另一个操作系统的后端，**不改动核心层**。
本阶段的产出不是「支持 Linux 或 macOS」这件事本身，而是**证明抽象层真的成立**。

分层原则、目录约束与能力协商的机制见
[architecture.md](../architecture.md) 第 12 节，本文只讲怎么做。

## 2 前置条件

| 项 | 状态 |
| --- | --- |
| 阶段一完成 | 接口已分层冻结，平台层目录与隔离检查已就位 |
| 与主线的关系 | 本阶段不参与 MVP 闭环，可在任意时间点启动 |
| 关键前提 | 契约测试先于任何平台实现，否则抽象层无法验证 |

## 3 平台差异对照

这是全项目**唯一**允许出现平台差异的部分。逐项对应一个已冻结的接口。

| 能力 | Windows 实现 | 抽象接口 |
| --- | --- | --- |
| 封禁下发与撤销 | WFP（`fwpuclnt`） | `IFilterEngine` |
| 进程标识与路径 | exe 的 NT 设备路径 | `ITargetResolver` |
| 连接枚举 | IP Helper 端点表 | `IConnMonitor` |
| 字节统计 | TCP 走 eStats，UDP 走 ETW | `ITrafficStats` |
| 连接中断 | `SetTcpEntry` | `IKiller` |
| 事件订阅 | ETW | `ISessionMonitor` |
| 提权检测 | 管理员令牌 | `IPrivilege` |
| 单实例 | 命名 Mutex | `ISingleInstance` |
| 自启动 | 计划任务 | `IAutoStart` |
| 配置与数据目录 | `%APPDATA%\BanIPHelper` | `IPaths` |
| 必备放行项 | 含 NCSI 等 Windows 概念 | `ISafetyGuard` 的放行清单部分 |

> 其他平台的对应技术选型在本阶段实施时再定，**不在现在就写死**。
> 需要遵守的只是：每个能力都必须落到上表某一行的接口上。

## 4 步骤清单

| 步骤 | 内容 | 产出物 | 验收 | 依赖 | 并行 |
| --- | --- | --- | --- | --- | --- |
| S8.1 | 契约测试套件与内存实现：把每个平台接口的契约写成测试，并提供内存实现供持续集成与界面开发使用 | 契约测试与内存后端 | 内存后端全部契约测试通过 | S1.2 | 否，最先 |
| S8.2 | 后端装配：编译期选择启用哪个后端，同一构建产物不混用多平台实现 | 后端装配模块 | 切换后端只需改构建配置，不改核心代码 | S8.1 | 否 |
| S8.3 | 新平台后端实现：按第 3 节对照表逐项实现，做不到的能力如实声明为不支持 | `platform/<os>/` 实现 | 契约测试通过，且能力声明与实际行为一致 | S8.2 | 是 |
| S8.4 | 界面与对外接口的能力适配复核：所有被禁用或降级的能力都有明确表现 | 适配复核记录 | 不存在静默失败的能力路径 | S8.3 | 否 |
| S8.5 | 平台化打包：各平台的运行时依赖收集与分发方式 | 打包脚本 | 目标平台干净环境可安装并运行 | S8.3 | 是 |

## 5 并行编组

| 编组 | 步骤 | 并行安全性依据 |
| --- | --- | --- |
| A 基座 | S8.1 到 S8.2 | 契约测试与装配先于任何平台实现 |
| B 多平台 | S8.3 可同时开多个平台各自一份 | 平台实现之间互不引用，唯一的共同点是契约测试 |
| C 收尾 | S8.4、S8.5 | 分别在不同层面收口，两者彼此独立 |

## 6 契约测试清单

契约测试是抽象层成立与否的唯一判据，任何平台后端都必须全过。

| 接口 | 契约要点 |
| --- | --- |
| `IFilterEngine` | 下发后可枚举到；撤销后无残留；重复下发幂等；失败时不留半成品 |
| `ITargetResolver` | 能解析为稳定的进程标识；进程退出后标识失效可被识别 |
| `IConnMonitor` | 快照与增量一致；协议与地址族覆盖完整；无重复上报 |
| `ITrafficStats` | 计数单调不减；不支持时必须返回明确的不支持而不是零 |
| `IKiller` | 中断后连接确实消失；不支持时必须明确报错 |
| `ISessionMonitor` | 订阅与退订成对；进程退出时资源释放 |
| `IPrivilege`、`ISingleInstance`、`IAutoStart`、`IPaths` | 权限判定准确；单实例可靠；自启可注册可撤销；目录可写且位置符合平台惯例 |
| `ISafetyGuard` | 放行清单按平台提供；回滚在任何情况下都能回到上一可用配置 |

## 7 阶段验收

1. 新增一个平台只增加一个目录与一份实现，核心层零改动
2. 内存后端与真实后端跑同一套契约测试，结果一致
3. 各后端的能力声明与实际行为一致，不存在声明了却做不到的能力
4. 界面与对外接口对被禁用能力有明确表现，无静默失败
5. 目标平台干净环境可安装并运行

## 8 风险与对策

| 风险 | 对策 |
| --- | --- |
| 抽象层被绕过，平台概念渗进核心层 | 依赖阶段一的构建期检查，评审时对核心层出现平台概念一律打回 |
| 接口设计过度迁就某平台 | 接口只描述「要做什么」，不描述「怎么做到」；平台专有参数一律留在实现内 |
| 新平台能力缺失被隐藏 | 能力协商是硬性要求，做不到就如实声明，界面显式禁用 |
| 为跨平台牺牲 Windows 侧能力 | Windows 是本阶段主线，抽象层不得削掉现有能力；必要时通过能力位区隔 |

## 9 交付物清单

- 平台接口的契约测试套件
- 内存后端实现
- 后端装配机制
- 至少一个新平台的完整后端
- 能力适配复核记录
- 平台化打包脚本
