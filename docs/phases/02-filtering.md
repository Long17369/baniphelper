# 阶段二 封禁能力

## 1 目标与范围

把规则模型完整转化为 Windows 过滤平台的过滤器，覆盖 IPv4 与 IPv6、TCP 与 UDP、
出站与入站、端口与网段，并支持立即中断已建立的 IPv4 连接。

本阶段**不涉及界面与记录**，只保证「封得住、撤得净、重启还在」。

### 2.1 实施 S1.7 时挖出来的两个平台事实

这两条都由实测确认，不是推断。它们直接决定 S2 的代码怎么写，因此提前记在这里。

**其一：MinGW 的 WFP 头没有层与条件字段的 GUID。**

`fwpmu.h` 只 `DEFINE_GUID` 了三个 provider 常量，`FWPM_LAYER_*` 与 `FWPM_CONDITION_*`
**一个都没有**；`libfwpuclnt.a` 也只导出函数，不导出这些 GUID 符号。
所以「不需要 Windows SDK」这个结论仍然成立，但代价是：**层与条件的 GUID 必须自己维护一张常量表**，
取值来自微软文档（属于 WFP 的 ABI，不会变）。

维护这张表有两条纪律：

1. **取值必须逐个校验**，不能照记忆写。校验办法是现成的：
   `FwpmLayerEnum0` 会列出系统里全部层的 `layerKey`，拿候选值去比对即可。
   这张表已经落地（S1.15）：取值、出处与核对工具见
   [01-foundation.md](01-foundation.md) 的 S1.15 与 `src/platform/win/wfp_guids.h`。
   其中 10 个层常量已在本机运行时 **10/10 全部对上**，
   S2.6 需要的入站 UDP 数据报层就在其中，届时不必再单独确认。
2. **层名不能用来认层**。系统里层的 `displayData.name` 是资源串或短分类名
   （实测取到的是 `ALE`、`IP`、`RPC` 这类，甚至空串），靠名字区分不出是哪一层。

写错层 GUID 的后果很隐蔽：过滤器会落在别的层上，表现成「规则明明下发了却不起作用」，
而且不会报错。所以校验这一步不能省。

**其二：枚举过滤器必须同时给出 provider 与层。**

`FwpmFilterCreateEnumHandle0` 的模板里，`layerKey` 留空会被 WFP 以
`FWP_E_LAYER_NOT_FOUND`（`0x80320004`）拒绝；只给 `providerKey` 不够。

因此「找出本工具的全部过滤器」只能是：先 `FwpmLayerEnum0` 拿全部层，
再逐层用本工具的 `providerKey` 过滤一遍。

**不要改成写死一份层清单**：清单必须随功能扩展而增补，只要有一次忘了补，
那一层上的旧过滤器就永远清理不掉，而且清理还会报告成功 —— 是静默失败。
逐层问一遍的代价是启动时多几十毫秒，换的是清理的完整性不依赖人记得改。

另外一个结构细节：`FWPM_FILTER_ENUM_TEMPLATE0::providerKey` 与 `FWPM_FILTER0::providerKey`
是 `GUID*` 而不是值，要传地址；常量是 `const`，得先拷一份可写的出来。

### 3.1 实施 S2.1 时的四个决定

产出是 `src/core/rule_model.{h,cpp}` 与 `tests/rule_model_test.cpp`，新增 CTest 目标 `rule_model`。
断言的落点刻意放在「该拒的有没有全拒」与「错误信息说不说得清」上，
而不是「功能跑得通」——这个模块最坏的失败方式不是崩溃，而是**把错误语义当成合法规则收下**。

#### 地址解析借 QtNetwork 的 QHostAddress

IPv6 的写法太多（压缩零段、内嵌 IPv4、十六进制大小写），自己写解析器容易在边界上出错，
而地址解析错的后果是**静默封错范围**：过滤器落在别的地址上、不报错，
现象是「规则明明下发了却没封住」，正好撞在本项目最怕的失败方式上。
`QHostAddress` 是跨平台的纯值类型，不涉及任何平台专有头，因此不违反 S1.10 的隔离约束。

代价是核心层新增一个依赖：`Qt6::Network`，并且**用 PRIVATE 链接**——
头文件里不出现 `QHostAddress`，地址解析纯粹是核心层的内部实现细节，不必传给上层。

顺带清掉了界面目标上的一条既存配置警告：`src/ui` 链了 `BanIPHelper::Core`，
而 `Core` 公开依赖 `Qt6::Sql`（S1.6 引入），界面目标自己的 `find_package` 里却没声明 `Sql`，
Qt 在 finalize 可执行文件时会报「mentioned as a dependency but not declared」。
现在界面目标的依赖清单里补上了 `Sql`。

#### 全匹配条件不许取反，这是硬拒绝而不是宽条件标记

`any` 与 `both` 取反之后没有任何取值能命中，整条规则会永不生效。
这种规则看上去封了一批东西、实际一条都不封，属于最危险的一类失败：
用户以为已经封住了，于是不再检查。所以 `validateRule` 直接拒绝并说清后果，
而不是像别的宽条件那样只挂一个风险标记。

#### 具体度的档差必须远大于取反加成

第 4.6 节要求「取反条件的优先级略高于同方式」，这条要求有个隐藏的下限：
加成一旦接近档差，「多加几个取反条件」就能把规则抬到更具体的档位上，
于是**规则看起来越具体反而越不优先**。取值方式是「档位分 1000 / 900 / 800……，
最小档差 100；取反加成固定 1」，并把「最小档差 > 取反加成 × 域数」
写成了测试里的断言，而不是留在注释里。

#### 同一个域只允许出现一个条件

两个同域条件是**交集**语义：`port ∈ {80}` 且 `port ∈ {443}` 恒为假。
用户几乎一定是想表达并集，所以 `validateRule` 拒绝并指出正确写法——
把多个取值放进同一个条件的取值列表。这条约束同时保证一条规则最多只有 5 个条件，
上面那条断言才算得出确切的上界。

### 3.2 实施 S2.2 时的一次实测修正

产出是 `src/platform/win/filter_plan.{h,cpp}` 与 `tests/filter_plan_test.cpp`，
新增 CTest 目标 `filter_plan`。

这一步最初的写法是**把每个取值都拆成一条过滤器**：两个程序乘两个端口就是四条，
再跟方向、地址族、协议的维度做乘积。理由是「平台的一条 filter 里每个字段只能有一个取值」。
实测把这个前提推翻了。

#### 实测：同一条 filter 里同一字段的多个条件是「或」

做法分两步，脚本是 `tmp/probe-fw-multivalue.ps1` 与 `tmp/probe-fw-or-semantics.ps1`（都不入库）。

先看系统自己怎么用。给一条 Windows 防火墙规则填两个远程地址，把 WFP 的过滤器导出来，
结果是**一条** filter，里面 `FWPM_CONDITION_IP_REMOTE_ADDRESS` 出现了两次；
而填两个远程端口时，两个端口各占一条 filter。也就是说 Windows 防火墙自己就在混用两种做法。

单看形状还不够：「一条 filter 里同字段两个条件」到底是「与」还是「或」，
推断错了后果完全相反 —— 若是「与」，两个地址的规则恒为假、**一条都拦不住**。
所以做了一次真实连接验证：

| 步骤 | 操作 | 结果 |
| --- | --- | --- |
| 对照一 | 连一个公网目标，确认现在连得上 | 通 |
| 对照二 | 加一条阻止该地址的出站规则后再连 | 不通，规则确实生效 |
| 对照三 | 删掉规则后再连 | 恢复 |
| 关键实验 | 改成阻止「该地址 + 一个不存在的地址」，再连该地址 | **不通** |

关键实验不通，就说明同字段多条件是「或」——「与」的话那条规则恒为假，不可能拦住任何东西。

> 这个实验第一版是拿本机 loopback 当目标的，对照组就没通过：
> Windows 对本机到本机的流量有豁免，阻止规则压根不参与判定。
> 换成真实公网地址才成立。**对照组不通过时结论不可信，宁可说无效也不要照写。**

#### 于是展开维度从六个降到三个

现在只有三个维度会在**层**上产生分叉，各自一条过滤器：

| 维度 | 为什么必须分 | 依据 |
| --- | --- | --- |
| 方向 | 出站与入站是两个不同的层 | [architecture.md](../architecture.md) 第 3 节 |
| 地址族 | IPv4 与 IPv6 是两个不同的层 | 同上 |
| 入站 UDP | UDP 没有连接建立这一步，接收授权之外还要一条数据报层 | 同上 |

条数 = 落点数 × 地址族数，最多 3 × 2 = 6。多地址、多端口、多程序路径只让**条件**变多：
它们放进同一条过滤器的同一个字段下，靠「或」语义生效。用例里的数字全部写死在测试中，
不写成「大于 0」，因为条数会被拿去与实际下发的条数对账。

#### 取反不能跟着合并

正向的多值可以合并，取反的多值**绝对不行**。
`addr ∉ {A, B}` 若写成「≠A 或 ≠B」，这个条件恒为真（同一个地址不可能既等于 A 又等于 B），
等于把地址条件整个丢掉 —— 规则会**比预期封得宽**。

所以展开期**不求补**，把 `negate` 原样交给平台层：单值取反可以直接用「不等于」匹配，
多值取反必须先算出集合的补集，再用补集里的正向取值各出一个条件。
这条约束写在 `FilterCondition::negate` 的注释里，并且有一条测试锁住展开器交出去的形状。

#### 拆法放在 platform/win，这是本步骤唯一的架构取舍

按本项目的原则，「规则求值」是跨平台的部分，展开器理应放在 `core/`
（[README.md](../README.md) 第 8.3 节）。这一步**刻意放在 `platform/win/`**：
拆法允许与平台的过滤机制贴紧，代价是将来新增一个平台要重写一遍拆法。

它仍然是不含任何平台专有头的纯逻辑（因此能独立单元测试），
所以真要跨平台复用时，把 `filter_plan.{h,cpp}` 整体上移到 `core/` 即可，依赖方向不用动。
把它翻成 `FWPM_FILTER0` 的翻译层才是真正平台相关的部分，那一层属于 S2.4。

### 3.3 归一化该放在哪一层

S2.1 最初自己写了一个「去掉尾部多余分隔符」的函数，里面带着这样的判断：

```cpp
if (result.size() == 3 && result.at(1) == QLatin1Char(':')) {
  break;  // 保留「D:\」
}
```

那行盘符判断是**纯 Windows 的东西**，却出现在核心层里 —— 而本项目最硬的一条约束是
「平台差异只允许出现在 `platform/` 下」（[README.md](../README.md) 第 8.2 节）。

发现问题后的第一次修法是改用 `QDir::cleanPath`，把路径统一成 Qt 的规范形式（正斜杠）。
**那个修法本身也是错的，而且错得比原问题更值得记一笔**：它把「归一化」当成了目标，
而归一化根本不该发生在存储层。

换成 `cleanPath` 之后，`D:\games\A` 与 `D:/games/A` 确实收敛成了一个取值，
但代价是**用户写的路径被程序改掉了**：界面上出现正斜杠形式，`..` 会被解开，
UNC 写法会被改写 —— 数据一旦存进去就回不到用户写的样子。

正确的分界是这样：

| 关注点 | 放在哪 | 做什么 |
| --- | --- | --- |
| 存储 | 值校验 | 只判断「合不合法」，**一个字符都不改** |
| 比较 | `sameProcessIdentity` | 按平台规则归一（大小写、分隔符方向） |

「两个路径是不是同一个文件」本来就依赖平台，而且只在该判断的时候才需要判断。
存进去的是用户的原话，比较的时候才翻译 —— 于是界面上不会出现「我没写过的形式」，
存储层也不必维护一套可能与平台不符的改写规则。

所以路径的三个模式（可执行文件、通配、目录）现在**只校验、不改写**。
同一字段里 `C:\Tools\a.exe` 与 `C:/Tools/a.exe` 会各留一个取值，
这**不影响语义**：同字段的多个条件之间是「或」，两个等价条件不改变判定结果。

> 顺带说清 IP 与端口为什么还在改写：`2001:DB8::1` 与 `2001:db8::1`、`080` 与 `80`
> 是**同一种写法的不同拼法**，改写不会让人认不出来，而且这些值要参与数值运算
> （网段要展开成区间、端口要算范围）。路径不一样：它是**字符串身份**，
> 没有任何运算需要它规范化。

顺带查了同类问题：`sameProcessIdentity` 原先只归一大小写、没归一分隔符方向，
同样会表现为「同一个程序被当成两个」。它是要补的那一处 ——
归一放在**比较**这一层，而不是存储这一层。

> 还有一处平台相关的判断**刻意保留**在核心层：路径里的非法字符检查（`"<>|` 与通配字符）。
> 它要在用户「敲完就报错」的时刻给出反馈，而那时还没有任何平台调用。
> 真的做别的平台（S8）时，这里要按平台替换规则，或者下沉成平台接口的一个方法。
> 代码里已经这么标注了。

### 3.4 实施 S2.4 时的实测与五个决定

产出是 `src/platform/win/filter_engine.cpp` 里的下发与撤销、`filter_plan.{h,cpp}` 里新增的
`resolveNegation`、核心层 `rule_model.{h,cpp}` 里新增的取值求补，外加两个探针与一个演练：

| 文件 | 作用 |
| --- | --- |
| `tmp/probe_wfp_fields.cpp` | 用 `FwpmLayerGetByKey0` 摊开各层的**权威字段清单** |
| `tmp/probe_wfp_apply.cpp` | 逐条试「层 × 字段 × 匹配方式」能不能被系统接受 |
| `tmp/drill-s2.4.cpp` | 调真实引擎跑下发、幂等、撤销、对账与失败路径 |

#### 地址条件在 ALE 层上只有不带版本后缀的那一个

第一版实现给地址条件用了 `FWPM_CONDITION_IP_REMOTE_ADDRESS_V4` / `_V6`，
理由是「取值宽度与地址族一一对应」。探针一跑，**所有带地址条件的过滤器全部加不进去**，
错误码 `0x80320002`。

这个错误码不该靠猜，于是写了第二个探针，直接用 `FwpmLayerGetByKey0` 把层的字段清单读出来 ——
`FWPM_LAYER0` 本身就带 `numFields` 与 `FWPM_FIELD0` 数组，权威且可核对。结果是：

| 层 | 字段清单里的地址条件 | 取值宽度 |
| --- | --- | --- |
| `ALE_AUTH_CONNECT_V4` | `IP_REMOTE_ADDRESS`（**无后缀**） | `UINT32` |
| `ALE_AUTH_CONNECT_V6` | `IP_REMOTE_ADDRESS`（**无后缀**） | `BYTE_ARRAY16` |
| `ALE_AUTH_RECV_ACCEPT_V4/V6` | 同上，各按本族 | 同上 |
| `DATAGRAM_DATA_V4/V6` | 同上，各按本族 | 同上 |

带 `_V4` / `_V6` 后缀的那两个常量是给 IP 层（转发层、入站 IP 包层之类）用的，
在 ALE 三层上**根本不存在**。于是结论有两条，都得记住：

1. 条件标识**不带**版本后缀，取值宽度**按层**给（同一个字段，两种层两种宽度）；
2. 宽度给错不会报错，系统会把那串字节解释成别的地址 —— 规则于是封到别处去了。
   这正是本项目最怕的失败方式，所以这一条有测试锁住（求补与端口宽度）。

#### 数据报层没有程序标识，于是「程序 + 入站 UDP」表达不出来

同一张清单显示，`DATAGRAM_DATA_V4/V6` 的字段里**没有** `ALE_APP_ID`。
而展开器在「方向不限」时会同时产出接收授权层与数据报层的条目，
所以在数据报层的条目上带程序条件，那一条**加不进去**。

处理方式是**整体拒绝并说明**，而不是「下发能下发的那两条」：

```text
对入站 UDP 按程序限定的规则：当前平台不具备该能力（Windows 的 UDP 数据报层没有
程序标识这个条件，只有接收授权层有。请把这条规则的方向改成只看出站，
或者改用地址、端口来限定范围）
```

这与「只支持 IPv4 的平台遇到 IPv6 条目必须整体报错」是同一条原则：
**悄悄少下发一部分的后果是「规则看着生效了、实际留着一个缝」**，比拒绝危险得多。
错误信息里给出了两条可行改法，因为拒绝本身不该是终点。

#### 权重的上限是 15，于是优先级按千位压缩

探针确认：`FWP_EMPTY`、`FWP_UINT8` 的 0 与 15 都被接受，16 被拒。
`FWP_UINT64` 也被接受（100 与 100000 都通过），但**没有验证它是否真的按数值排序**，
所以不拿它当依据。

核心层的优先级是「动作基址 + 具体度之和 + 取反加成」，`allow` 从 10000 起、
`block` 到 5005 封顶，靠数值区间保证「放行永远赢」。压进 0–15 的办法是除以 1000：
`block` 落在 0–5、`allow` 落在 10–15，两边仍然分得开。

代价是**同一大档内的精细次序丢失**（1000 与 1900 都变成 1）。这不影响正确性：
同一档内要么都是阻断、要么都是放行，不存在「谁该赢」的问题。

#### 取反改成一律求补，不再依赖平台的不等匹配

S2.2 当时的打算是「单值取反交给平台的不等匹配，多值才求补」，理由是前者更省。
实施时改成了**一律求补**，理由有两条：

1. 「平台有现成的『不等于』」这件事**没有验证过**；
2. 求补是纯取值运算，正确性在核心层就能测，而依赖平台匹配类型就只能在真机上测。

代价是单值取反会从一条变成两段区间。但这个代价是**有界**的：
一段区间取反最多变成两段（起点的前面与终点的后面），不会有组合爆炸。

反过来，多值取反**必须**求补，这一点没有选择余地：
`addr ∉ {A, B}` 若翻成「≠A 或 ≠B」是恒真的（同一个地址不可能既等于 A 又等于 B），
等于把地址条件整个丢掉，规则会比预期**封得宽**。

还有一个必须堵的口子：**补集可能为空**。`addr ∉ {0.0.0.0/0}` 是一条永远不命中的规则，
放它过去会被翻成「不限定地址」—— 与用户的意图正好相反。所以求补为空时一律报错。

程序域是唯一求不出补集的字段（补集是「系统里除这几个之外的全部程序」，开放集合），
所以程序域的**多值**取反直接报错，单值取反保留标记交给平台的不等匹配。

#### 幂等靠「先删后加」，而它真的可行

重复下发同一条规则要先删掉旧的再下发新的。顺序不能反：换成「先加后删」，
中间那一瞬间新旧两份同时生效，而用户改规则的目的多半是**收窄**封禁范围 ——
那一瞬间会封得比预期宽，而且只在重下发时出现，极难复现。

「同一个事务里先删后加」这件事事先没有依据，探针也没覆盖，是演练里确认的：
重复下发三次之后过滤器条数不变。

#### 演练结果

`tmp/drill-s2.4.cpp`（需提权）跑下来全部通过，逐条对应接口契约：

| 断言 | 对应契约 |
| --- | --- |
| 出站 + 程序展开成 2 条（IPv4 / IPv6 各一），出站 + 网段 1 条 | 条数确定、可对账 |
| 重复下发三次之后总数仍是 3 | 幂等 |
| 程序 + 不限方向的规则被拒绝，且**不留任何过滤器** | 不支持的过滤族如实报错、事务回滚 |
| 撤销后无残留、再次撤销仍成功 | 撤销幂等 |
| 增删 100 次之后总数回到 0 | 阶段验收第 8 条 |

#### 顺带补上一个漏声明

`OrphanCleanup`（清理上次运行残留的自有过滤器）从 S1.7 起就实现了，
三种终止方式的演练也做过，但它**一直没被声明**。后果是界面上那一栏会显示成「做不到」，
而它明明做得到 —— 这同样是「声明与实际不一致」，方向相反而已。
契约测试里那条断言因此从「必须不声明 `FilterIPv4`」改成了「每个后端的声明与它的实现进度一致」。

#### S2.3 的范围按这一步的实测收窄

S2.3 原定内容是「可执行文件路径到设备路径的转换、进程存活跟随、短路径与大小写处理」。
第一件事在 S2.4 里被系统的 `FwpmGetAppIdFromFileName0` 顶替掉了：
它接受 DOS 路径、按当前系统的卷映射解析，卷序号、符号链接、短路径都由它处理。
自己拼一份 NT 设备路径等于把这套映射规则抄进我们的代码，
抄错了规则会落到**别的程序**上，而且不报错 —— 这正是本项目最怕的失败方式。

所以 `ITargetResolver` 剩下的价值只有「进程存活跟随」，而它真正被需要的地方是
S3 的连接观测（要把连接记录归到某个程序上）。这一步不预先实现它。

### 3.5 实施 S2.5 时的实测：出站封禁

产出是 `tmp/drill-s2.5.cpp`（必须提权运行）。S2.4 验的是「过滤器下发得对、撤得净」，
**没有验过它真的拦得住流量**。这一步拿真实连接去撞，每一组都带对照组：

| 用例 | 目标 | 条件 | 预期 |
| --- | --- | --- | --- |
| 对照组 | 公网地址 :443 | 无规则 | 连得上 |
| 按地址封 TCP | 同上 | 地址 + TCP + 出站 | 连不上 |
| 撤销 | 同上 | 撤销之后 | 立刻恢复 |
| 按地址封 UDP | 公网地址 :53 | 地址 + UDP + 出站 | 收不到应答 |
| 程序条件筛选 | 同上 | 程序 = 另一个可执行文件 | 本进程不受影响 |
| 程序条件命中 | 同上 | 程序 = 本进程 | 本进程被拦住 |
| IPv6 | 链路本地对端 | 地址 + TCP + 出站 | 连不上 |

#### 阻断的表现是「超时」，不是「连接被拒绝」

这是这一步最值得记下来的一条。被拦住时 `connect` **既不成功也不失败**，
在整个 5 秒的窗口里一直挂着（演练自己的超时给出 `WSAETIMEDOUT`）。
对照组撤销之后 94–1031 ms 就能连上，两者不会混淆。

常见说法是「ALE 层返回 BLOCK 会让 `connect` 立刻失败并报 `WSAEACCES`」。
实测不支持这个说法，所以代码与界面文案里**不许**把「立刻报错」当成判据。

#### UDP 被拦下的表现与 TCP 不同

`sendto` **成功返回**，但应答再也收不到。也就是说 UDP 这条路径上是
「授权层放行、由数据面丢弃」，**不能用 `sendto` 的返回值判断有没有封住**。
这一条直接影响 S3 的观测设计：UDP 的流量不能靠发送失败来计数。

#### 程序条件确实在筛选

规则里写「程序 = 另一个可执行文件」时本进程照常连得上，写「程序 = 本进程」时立刻被拦住。
两次的唯一差别就是程序条件的取值，所以「程序条件被忽略、规则作用到了所有程序」
这个失败模式被排除掉了。

#### IPv6 必须单独验，而本机没有 IPv6 出口

本机**没有任何 IPv6 全局地址，也没有 `::/0` 默认路由**，所以「连不上」分不清是
「没路由」还是「被封」。解决办法是用**手机热点链路上的链路本地地址**：
手机连在电脑开的热点上，两台机器在热点链路内有真实的 IPv6 链路本地地址
（主机 ping 通，往返 65–73 ms），这条链路不是 loopback，可以真的验拦截。

先记一个反面结论：**错误码本身不能当判据**。
在无 IPv6 出口的目标上，有无规则都是同一个错误码，那种「对比错误码」的做法
什么也证明不了（第一版演练就是这么写的，结论被判为无效）。

#### 核心层刻意拒绝带作用域标识的地址

链路上要连 `fe80::…%22`，但 `fe80::…%22` **不能写进规则**：
核心层的 `parseAddress` 当场拒绝，理由是「带作用域的地址只在链路本地场景有意义，
过滤条件里的地址不带它；与其悄悄丢掉作用域，不如当场拒绝」。

于是演练的连接用带作用域的地址、规则用不带作用域的地址
（过滤器里的地址字段本来就只有 16 字节，作用域是接口的事）。
演练把「带作用域的地址被拒绝」也做成了一个断言，免得将来有人把它当成漏网改掉。

这条约束要在界面上让用户看得见（S5）：用户从连接列表里把一条链路本地连接
拖成规则时，程序必须说清「作用域不会被写进规则」。

### 3.6 实施 S2.6 时的实测：入站封禁

入站与出站不同：**必须由一个真正的外部发起方来验**。
本机自己连自己走 loopback，被系统豁免，阻止规则根本不参与判定（S2.2 那次就栽在这上面）。

试过而不可行的三条路，都记下来免得重复踩：

| 路子 | 为什么不行 |
| --- | --- |
| 本机自连 | loopback，被系统豁免 |
| WSL（镜像模式） | WSL 把主机地址当成自己的，连过去返回「连接被拒绝」 |
| VirtualBox 虚拟机 | 只有 NAT 网卡，guest 连主机最终走宿主机 loopback |

可行的办法是**手机连电脑开的热点，用 Termux 当发起方**。
热点接口上主机是 `192.168.137.1`、手机是 `192.168.137.186`，这是一条真实的链路。

#### 必须临时加一条系统防火墙放行规则

系统防火墙默认挡掉一切外部入站。不加放行规则的话**对照组本身就通不了**，
也就分不清「连不进来」是防火墙挡的还是我们的过滤器挡的 —— 结论不可信。
所以演练前加两条只针对测试端口的放行规则（TCP 15001 / UDP 15002），跑完立刻删，
再查一遗确认残留为零。改动范围仅限这两条规则，不碰防火墙开关与其他现有规则。

#### 时间线从「收到第一个包」开始，两边不对表

手动驱动的对端没法卡时间点，所以演练**不假定对方什么时候开始**：
收到第一个包才开始计时，之后 15 秒无规则 → 15 秒入站阻断 → 15 秒撤销。
对方早一点晚一点都只影响等待时长。

另一个让两边不用对表的办法：主机接受连接时回一个带阶段标记的响应
（`PHASE-1` / `PHASE-2` / `PHASE-3`），手机那边一眼就能看出每次连上的是哪个阶段。

#### 入站演练的结果

四条组合（TCP/UDP × IPv4/IPv6）分开计数，不合并。下表是每一阶段收到的包数：

| 组合 | 无规则 | 入站阻断 | 撤销后 |
| --- | --- | --- | --- |
| TCP-IPv4 | 11 | 0 | 12 |
| TCP-IPv6 | 11 | 0 | 12 |
| UDP-IPv4 | 8 | 0 | 12 |
| UDP-IPv6 | 9 | 0 | 11 |

两条入站规则合计 **6 条过滤器**（TCP 入站接受 v4/v6 两条；UDP 入站接受 v4/v6
加数据报 v4/v6 四条），与展开器的预期逐条对上 ——
这也是「入站 UDP 必须补数据报层」这条设计的当场核对。

#### 教训：验证脚本里的每一次尝试都必须有自己的超时

第一版手机侧的循环用 bash 的 `/dev/tcp` 连，而**它没有超时**：
被拦住的那一次连接会挂住二十秒以上，整轮被拖住，于是撤销阶段一个包都没发出来，
日志上看起来像「撤销之后没恢复」，实际是脚本卡住了。

所以「被拦住了」与「卡住了」在日志里长得一样，
**每一次尝试都必须有自己的超时**（改成 python 的 `settimeout` 之后一次通过）。

### 3.7 实施 S2.7 时的实测：端口与网段

产出是两个演练：`tmp/drill-s2.7.cpp`（出站：远端端口与网段）与
`tmp/drill-s2.7-in.cpp`（入站：本地端口语义与不误伤）。两者都做成「三阶段时间线
＋逐条带对照组」，入站那一个仍然用手机当外部发起方。

#### 端口条件的方向语义：出站取远端、入站取本地

这是这一步最要紧的一条，之前只有代码注释、没有实测。

| 方向 | 规则 | 结果 |
| --- | --- | --- |
| 出站 | 阻断 TCP 端口 443（不限地址） | 443 变成超时；**同一个地址的 80 与 853 照常连上** |
| 出站 | 阻断 800-900 区间 | 区间内的 853 被封；区间外的 443 与 80 不受影响 |
| 出站 | 阻断 {80, 853} 两个取值 | 两个都被封；没列进去的 443 不受影响 |
| 入站 | 阻断本地端口 15001 | :15001 收不到连接；**同一个发起方连 :15011 照常进来** |

出站那三条里「同地址、同进程、换个端口不受影响」就是验收里的「不误伤」；
入站那一条的关键是 :15011 在阻断期间仍然有连接进来 —— 同一个外部发起方、同一台主机，
只因为本地端口不同就不受影响，才能说明端口条件确实取的是**本地**端口，
而不是被错映射成对端那个随机的源端口（后者永远不可能命中）。
IPv4 与 IPv6 两族分开计数，两族都通过。

#### 网段是按网段匹配的

| 规则 | 结果 |
| --- | --- |
| 阻断出站到 `223.5.5.0/24` | 223.5.5.5 被封；**相邻网段的 223.6.6.6 不受影响** |
| 一条规则里写 `{223.5.5.0/24, fe80::/64}` | 按地址族切成 **2 条**（IPv4 一条、IPv6 一条），两边都生效 |

混族那一条同时盖住了三件事：一条规则可以带多个网段、混合地址族会按族拆开、
IPv6 段确实参与判定（对照组的 IPv6 对端从 31 ms 连上变成超时，撤销后又变回 31 ms 连上）。

条数与展开器的预期逐条对上：单个 IPv4 网段 1 条；含 IPv6 的混族规则 2 条；
不限地址的端口规则 2 条（两族各一）；入站本地端口规则 2 条（两族各一）。

#### 判据不能跨对端通用：关闭端口的反应随目标而变

建立这套演练时想用一个省略对端的办法：对关闭的端口，本机应当很快收到 RST，
而「被封」是静默丢弃，于是「立刻拒绝 → 超时」就成了判据。

实测把这个想法推翻了两遍：

- `223.5.5.5` 上关闭的端口（9999 / 9985）是**静默丢弃**，不是 RST；
- 手机在热点链路上对关闭的端口也是静默丢弃。

而且我一度把「热点关掉后本机直接报不可达、几十毫秒就失败」误读成「对端回了 RST」，
据此设计出的判据自然不成立。**那次探针的对端根本不在线** —— 这也是个教训：
对照组不成立时得出的结论，比没有结论更坑。

所以 IPv6 段那一节改成了要求一个**真的在监听**的对端：
对照组是「连得上」，封住是「超时」，撤销后又要「连得上」。

#### 一次不可复现的失败，以及它换来的断言

有一次演练里「撤销后 223.5.5.5 立刻恢复」判为失败（那一节用的是 5 秒判据）。
但紧接着的 IPv6 连接只用了 31 ms，所以查了一下，并在演练里加了两个东西：

1. 撤销之后先问一遍引擎侧还剩几条过滤器；
2. 恢复尝试改成三次机会，并且每一次的耗时都打出来。

复跑时这两条都干净：「撤销后引擎侧一条都不剩（实际 0）」，且第 1 次就 31 ms 连上。
结论是**那一次是公网目标响应超时，不是撤销没生效**。
这条不改代码，但改演练：**把「网络抖了一下」与「功能没生效」分开**比多断言一条更重要。

#### 如实记下的两个缺口

| 缺口 | 原因 |
| --- | --- |
| 端口区间的**上界**没有被单独证明 | 区间 800-900 里唯一开放的端口是 853，852 与 854 都没开，找不到紧邻上界的对照组；下界那侧由 443 与 80 夹住 |
| 出站**远端端口**在 IPv6 侧只有条数证据 | 不限地址的端口规则确实展开成两族各一条，但行为上只用 IPv4 目标验过；IPv6 侧验的是入站的本地端口语义 |

### 3.8 实施 S2.8 时的实测：IPv4 即时断连

产出分四块：

| 文件 | 作用 |
| --- | --- |
| `src/platform/win/killer.{h,cpp}` | `WinKiller`：删除传输控制块 |
| `src/platform/memory/killer.{h,cpp}` | `MemoryKiller`：对照物，不真的断，只记账 |
| `src/core/ban_action.{h,cpp}` | **先封后断**的编排，与平台无关 |
| `tests/ban_action_test.cpp`、`tmp/drill-s2.8.cpp` | 前者验顺序，后者对着真实系统验效果 |

#### 断连只有一条路，边界由它划定

手段只有 `SetTcpEntry` + `MIB_TCP_STATE_DELETE_TCB`（删掉传输控制块）。
边界因此也是硬的：

| 对象 | 能不能断 | 原因 |
| --- | --- | --- |
| IPv4 TCP | 能 | 就是它干的事 |
| IPv6 TCP | **不能** | 没有等价接口，而且不允许用户态发原始 TCP 报文，连自己构造 RST 都做不到 |
| UDP | **不能** | 没有建立与拆除这一步，也就没有可删的控制块 |

后两类都必须在**调用时明确报「不支持」并给出说明**，而不是静默返回成功：
用户看到「已断开」而连接其实还在，比看到「这条断不了」危险得多。
与能力声明的一致性也是断言的一部分（`canKill` 的答案与 `KillTcpV4` / `KillTcpV6` 必须对得上），
而且断言里**不写死**「本平台断不了 IPv6」——那是现状不是契约。

#### 「先封后断」不是口号，反例是真跑出来的

这条不变量靠嘴说没说服力，所以演练里直接把**顺序反了会怎样**也跑了一遍：

| 阶段 | 做法 | 结果 |
| --- | --- | --- |
| P2 先断后封 | 无规则时直接断掉已建立的连接，然后立刻重连 | 连接确实消失了，但**重连成功了** |
| P3 先封后断 | 下发规则 → 再断连接 → 再重连 | 连接消失，**重连被拦住** |

P2 那一格就是这个不变量的全部理由：`ALE_AUTH_*` 只在新连接时判定，
所以「断」本身不会阻止重连。顺序反了的话，重连恰好落在规则生效之前，
用户看到的现象是「点了封禁，连接闪了一下又回来了」。

P3 走的是真实编排函数 `applyBanAndKill`，结果「请求 1 条、断了 1 条、失败 0 条」，
而且连接表里确实查不到了（不是标记为待关闭）。

#### 判据用的是系统的连接表，不是「send 是不是失败」

契约要求「中断后连接确实消失」，而「send 失败」分不出
「连接被删了」与「对端只是没回」。所以主判据是 `GetExtendedTcpTable`：
断之前必须在表里，断之后必须不在。send 的返回值只当旁证打出来（实测是 `10054`）。

#### 编排为什么值得单独成一个模块

实现只有二十行，但它承担的是封禁链路里**唯一一条时序要求**。
界面上「封禁」会有好几处入口（连接列表、规则编辑器、托盘菜单、将来的 WebUI），
每处各写一遍顺序就一定有一处会写反，而写反的症状是「偶尔闪一下就恢复」，极难复现。
放在 `core/ban_action.{h,cpp}` 之后，顺序只有一处定义，而且能用假实现直接断言调用先后。

两条硬约束各有测试锁住：

1. **下发失败时一条连接都不许断**（断了却封不住，等于白白打断用户的连接）；
2. **下发成功之后才断**，清单为空时连断连实现都不去碰。

还有一条容易漏的：规则已经生效、断连那一步整体失败时，错误信息必须说清楚
「规则已下发，只需重试断开」，否则用户会以为整个操作失败了、去重新下发一遍。

#### 不存在的连接不许静默成功

拿一条格式合法但系统里根本没有的连接（本地地址用 TEST-NET-3，
不可能误删真实连接）去断，`SetTcpEntry` 返回了 **317（0x13D）**。
这个码不在 `winerror.h` 的标准表里，但重要的是它**不是成功** ——
这一层没有把「断了一条本来就不存在的连接」当成成功上报。

#### 顺带：平台后端多了一个成员

`PlatformBackend` 加了 `killer`，与 `filterEngine` 并列而**不合并**。
理由是两者的可用性依赖不同的东西：过滤器引擎只需要提起过权，
而断连在某些平台上根本做不到（IPv6 就是常态）。
合成一个之后，「规则能下发但连接断不掉」这个状态就表达不出来了。
装配点本来就写着「后续步骤按需要往里加（……断连……）」，所以这次不是接口变更。

#### 两个后端的行为必须一致

断连的判据在两个实现里**各写了一遍**，这看起来像重复，但是刻意的：
「IPv6 断不了」是**本平台**的事实，提到公共处会让将来某个真能断 IPv6 的平台
被迫承接一个错误的答案。契约测试因此只断言「能断就得声明、声明了就得能断」，
以及一条与平台无关的：**UDP 没有连接可拆，任何实现都必须给 false**。

### 3.9 实施 S2.9 时的实测：规则持久化与恢复

产出分四块：

| 文件 | 作用 |
| --- | --- |
| `src/core/rule_store_sqlite.{h,cpp}` | `SqliteRuleStore`：规则落库，含订阅通知 |
| `src/core/rule_runtime.{h,cpp}` | 生命周期编排：落库/下发/撤销/过期失效/启动恢复 |
| `src/core/database.cpp` 的迁移 2 | `rules` 表与 `(enabled, expire_at)` 索引 |
| `tests/rule_store_test.cpp`、`tests/rule_runtime_test.cpp`、`tmp/drill-s2.9.cpp` | 前两个是单元测试，第三个是跨进程的端到端演练 |

#### 表结构的三处取舍

`conditions` **存成 JSON 文本**，不另开一张条件表。条件是**整体**语义（域间交集、域内并集），
拆成行之后「一条规则的条件」要靠 join 拼回来，而条件没有独立于规则的生命周期。
代价是条件本身不可用 SQL 检索 —— 但本程序从来不按条件查规则。

时间一律存 **UTC** 的 ISO 8601（带毫秒）。`expire_at` 的到期判断走字符串比较（`expire_at <= ?`），
而字典序只有在**格式与时区都统一**时才等于时间序；混进一个本地时间就会有规则在该到期的时候不到期。
演练里专门验了「本地时间表示的取值也能正确往返」。

`created_at` **归存储层所有**：新增时用调用方给的，更新时忽略调用方给的值、保留库里那个。
它是「同具体度则先建的优先」的依据，被改写的话规则之间的先后会在**每次编辑后漂移**，
结果不再可复现。这条有专门的断言。

#### 读出来也校验，而且不许宽松解释

库是可以被手工改的，也可能是别的版本写的。遇到不认识的域或方式时按「大概是这个意思」
去理解，后果是**按错的语义封禁** —— 那比这条规则不生效危险得多。所以 `list()` 碰到一行坏数据
**直接失败并指出是哪一条**，而不是跳过它继续。测试里用 SQL 直接塞了一行 `domain = "nonsense"`
来验这件事。

#### 顺序与回滚：三条规矩

编排落在 `RuleRuntime`，单独成型的理由与 `ban_action` 同源 —— 写规则的入口将来会有好几处
（规则编辑器、连接列表右键、WebUI、导入），每处各写一遍顺序就一定有一处会写错，
而写错的症状是「库里显示启用、实际没生效」这种界面上看不出来的状态。

| 规矩 | 为什么 |
| --- | --- |
| **先下发、后落库** | 反过来的话，落库成功而下发失败会留下一条「库里写着启用、实际没生效」的规则 |
| **落库失败要把引擎恢复成原样** | 规则可能本来就存在，所以恢复动作是「把旧版本重新下发」而不是一律撤销 |
| **过期失效先撤、后停用** | 撤销失败就不许改启用状态：规则还在生效，库里的记录必须与事实一致 |

> 第二条的测试真有收获：它抳出了一个真 bug —— 「本来没有这条规则」时，回滚拿的是
> 默认构造的空壳规则，它去撤销的是**空标识**而不是那条规则，于是回滚等于没做，
> 恰好留下它本来要防的状态。断言写的是「日志里应有 `revoke:r1`」
> 而实际打出的是 `revoke:`，一眼就看出来了。

#### 到期不是内核自己会做的事

这一条是演练里顺手挖出来、但值得单独记的：规则过了过期时刻之后，**过滤器还在**。
`expire_at` 只是我们库里的一列，内核不知道它的存在，也不会有任何东西到点去动那些过滤器。

所以 `main.cpp` 里挂了一个**每分钟一趟的巡检**，启动时先跑一趟（收掉「上次退出之后才到期」的），
之后靠 `QTimer` 周期跑。演练里把两个时刻都量了：过期时间过后连不上（过滤器还在），
巡检跑完就连得上了，而且库里的启用状态也变成停用（重启不会把它再下发一次）。

#### 启动顺序：清理必须排在重建之前

`main.cpp` 里这两件事的顺序是**不变量**：先 `cleanupOrphans()`，再 `restore()`。
反过来的话，刚下发的规则会被当成「上次运行残留的过滤器」收掉 —— 规则永远不生效，
而且清理还会报成功。代码里把这个理由写在了调用点旁边。

#### 演练结果（跨两个进程）

| 阶段 | 断言 | 结果 |
| --- | --- | --- |
| seed | 建库（结构版本 2）、写入 3 条规则、下发 2 条，然后**不撤销就退出** | 通过 |
| verify | 新进程清掉上次留下的 **2 条** 过滤器；清理后两个目标都连得上（对照组） | 通过 |
| verify | 重建只生效 **1 条**（keep），已过期 1 条、已停用 1 条，三类加起来等于库里的条数 | 通过 |
| verify | 重建之后 `223.5.5.5:443` **真的连不上** —— 行为证据，不只是「列表里有它」 | 通过 |
| verify | 巡检把已过期的 `stale` 停用，且过期时间没有被抹掉（界面还要靠它显示「已过期」） | 通过 |
| verify | 实时过期：下发一条 3 秒后过期的规则 → 立刻封住 → 过了 3 秒**仍然封住** → 巡检后放开 | 通过 |

最后一条是这次演练里信息量最大的一行：它同时证明了「过期靠巡检」与「巡检确实有效」。

### 3.10 实施 S2.10 时的实测：一次性验证脚本

产出三块，都在 `tmp/` 下（不入库）：

| 文件 | 作用 |
| --- | --- |
| `tmp/drill-s2.10.cpp` | 下发三条**条数已知**的规则后**不撤销就退出**，把现场留给脚本去数；另有 `revoke` 模式收尾 |
| `tmp/probe-owncount.cpp` | **独立判据**：裸 WFP API、独立进程、不链后端也不链 Qt，逐层数自家过滤器 |
| `tmp/verify-s2.ps1` | 一条命令跑完阶段二的演练清单，并核对条数、落点层与收尾是否干净 |

验收标准是「脚本可独立复现封禁与撤销，不依赖界面」。真正的难点不在跑演练，
而在**怎么证明系统里的过滤器条数真的是某个数** —— 这一步几乎全部时间都花在这上面。

#### 第一步就找错了判据：正则切 XML 切出了假数据

最初的打算是拿 `netsh wfp show filters` 的 dump 当系统侧判据，用正则把 XML 里的
`<item>` 块切出来数。第一版读数与程序自报的 7 条对不上（只数到 3 条），
差一点就据此写下「引擎多报了 4 条」的结论。

查下去才发现问题出在自己身上：**dump 里的 `<item>` 是嵌套的**，
过滤器、过滤条件、防火墙规则共用这一个标签（全文件 8440 个 `<item>`，而过滤器只有 1986 条），
按 `<item>…</item>` 切出来的「块」根本不是过滤器。换成真正的 XML 解析之后读数变成 5 条。

> 教训很直接：**判据本身也得有判据**。一个坏掉的数数脚本和一个不漏人的数数脚本，
> 两者的输出长得一模一样（都是「和程序自报对不上」）。

#### 剩下的 2 条差不是误差，是 netsh 的盲区

用 XML 解析之后全局总数与自家条数**完全自洽**（1981 → 1986、0 → 5，两个差值都是 5），
所以不是解析问题。少的正好是「入站 + UDP」规则在数据报层落的那 2 条。

于是做了对照实验（`tmp/probe-dgram.cpp`）：同一个进程、同一个 provider、
同样是**无条件**的 block 过滤器，**只有层不同** —— 一条落在
`FWPM_LAYER_ALE_AUTH_CONNECT_V4`（已知 netsh 看得见），一条落在
`FWPM_LAYER_DATAGRAM_DATA_V4`（怀疑看不见）：

| 阶段 | 对照层 | 数据报层 |
| --- | --- | --- |
| `FwpmFilterAdd0` 返回 | `0x0` | `0x0` |
| `FwpmFilterGetByKey0` 按 key 回查 | 找到，层匹配 | 找到，层匹配 |
| `netsh wfp show filters` 的 dump 里 | **1 条** | **0 条** |
| 删除之后再回查 / 再数 | 都没有 | 都没有 |

结论：**`netsh wfp show filters` 不 dump `DATAGRAM_DATA` 层**。
本演练的「入站 + UDP」恰好在那一层落 2 条，于是它的读数天然是 `7 − 2 = 5`。
这不是误差，也不能靠「差 2 就放过」糊过去 —— 那样将来真漏一条时差值会是 4，
而 4 与 5 的区别没人会去看。

#### 自建主判据：裸 API、独立进程

既然现成的外部工具覆盖不全，就自己做一个判据，但必须满足两个条件才配叫判据：

1. **不链被测代码**：`probe-owncount` 用裸 WFP API 重写一遍逐层枚举
   （`FwpmLayerEnum0` 拿层清单 → 逐层 `FwpmFilterCreateEnumHandle0` + `FwpmFilterEnum0`），
   构建时用 `build-drill.ps1 -Bare` 只链 `fwpuclnt` 等系统库，
   不链 `baniphelper_core.a` / `baniphelper_backend_impl.a`，也不链 Qt；
2. **独立进程**：即使后端哪天把枚举写错，它给出的仍是系统侧的真值；
   顺带也证明了那几条过滤器是**系统里真的还在**，而不是某个进程内存里的账。

它按规则标识与层 GUID 分别汇总，输出 `OWN_TOTAL` / `RULE=<id> COUNT=<n>` / `LAYER=<guid> COUNT=<n>`，
脚本据此做三件事：核对总数、核对每条规则的条数、核对**逐层落点**。

#### 三个数放在一起看

| 判据 | 性质 | 本演练的读数 |
| --- | --- | --- |
| 程序自报 | 引擎逐层枚举系统（不是内存里的账），但仍是被测代码 | 7 条 |
| **独立判据** `probe-owncount` | 裸 API、独立进程、不链被测代码 | 0 → 7，且逐规则 2/1/4、逐层六层全中 |
| 旁证 `netsh` | 完全外部，但对数据报层有盲区（已实测） | 0 → 5，预期 `7 − 2` |

期望值不是从程序输出里读的，而是**脚本里独立写的一张层表**：

| 层 | 预期条数 | 来自哪条规则 |
| --- | --- | --- |
| `ALE_AUTH_CONNECT_V4` | 2 | `count-proc` + `count-subnet` |
| `ALE_AUTH_CONNECT_V6` | 1 | `count-proc` |
| `ALE_AUTH_RECV_ACCEPT_V4` / `_V6` | 各 1 | `count-udp` |
| `DATAGRAM_DATA_V4` / `_V6` | 各 1 | `count-udp`（UDP 没有连接建立这一步） |

#### 脚本整跑一遍的读数

```text
基线：独立判据数到自家 0 条；netsh 的 dump 里全系统 1981 条、自家 0 条
drill-s2.4 / s2.5 / s2.7 / s2.8 / s2.9   退出码 0，之后自家过滤器 0 条
drill-s2.6 / s2.7-in                     SKIP（需要外部对端，加 -WithPeer）
条数核对：独立判据 0 → 7；逐规则 2/1/4；逐层六层全中；netsh 旁证 0 → 5 = 7 − 2
收尾：0 条（干净）
=== ALL PASSED ===
```

`-WithPeer` 那两项默认跳过：它们要手机连在电脑热点上、并在 Termux 里手动跑一段连接循环
（见 3.6 / 3.7），而「脚本可独立复现」这条验收不该依赖手边正好有一台手机。
加 `-WithPeer` 时脚本会先把 Termux 里要跑的那段命令打出来。

#### 这一步没覆盖的东西

| 没覆盖 | 为什么，以及由谁覆盖 |
| --- | --- |
| **逐条过滤器的条件内容**没有自动比对 | 落点层与条数由本脚本核对；条件的**形状**由 `tests/filter_plan_test.cpp` 锁住（含地址宽度、取反求补、端口方向语义），跨机器复现需要把条件也 dump 出来，那属于观测能力（S3） |
| 数据报层的行为证据只有「条数 + 层」 | 行为上「入站 UDP 被拦住」由 3.6 的手机端对端演练证明，本脚本不重复做 |
| 只在 Windows 上跑 | 其它平台要到 S8，届时 `probe-owncount` 需要另一份平台实现 |

#### 工具链本身踩的三个坑

这一步的时间几乎都耗在这三件事上，都会让「脚本坏了」与「功能坏了」长得一样：

| 坑 | 表现 | 处理 |
| --- | --- | --- |
| `Measure` 是 `Measure-Object` 的内置别名 | 自定义的 `Measure` 函数被静默忽略，差值恒为 0 —— 而脚本照样打印「通过」 | 函数改名（`CountFilters` / `Get-OwnCount`），并把原因写在函数上方 |
| 提权进程里 `Add-Content -Encoding utf8` 失败 | 每行日志都报 `Stream was not readable`，日志**全丢**而脚本继续跑 | 改用 `[IO.File]::AppendAllText` |
| 终端回显显示的是**上一次**运行的输出 | 改完脚本重跑，看到的还是旧结果，一度以为改动没生效 | 关键结果一律落盘（`tmp/verify-s2.txt`、`tmp/inv-*.txt`）再读文件 |

第二条还有一层：**判据脚本自己坏了会给出假通过**。所以 `verify-s2.ps1` 现在
把每一项判定的依据都印出来（差值、逐规则条数、逐层落点、netsh 旁证），
而不是只印一句「通过」。

| `tests/filter_plan_test.cpp` | 新增 2 个断言函数；原来那条「wildcard 与 dir 尚未支持」的断言随之作废 |
| `tmp/probe-appid-match.cpp`、`tmp/inv-appid-*.ps1` | 前置实测的探针与驱动（不入库） |

#### 先搞清楚「程序」在系统里到底是什么

`ALE_APP_ID` 是 `FWP_BYTE_BLOB`，实测它的内容是**可执行文件 NT 设备路径的 UTF-16LE 字节**，
而且：

```text
\device\harddiskvolume6\fdm\baniphelper\tmp\appid-probe\a\connector.exe\0
```

两个性质决定了一切后续设计：

1. **全小写**。系统里那个设备名本身写作 `\Device\HarddiskVolume6`，而 `FwpmGetAppIdFromFileName0`
   返回的却是 `\device\harddiskvolume6` —— 也就是说这一层自己会小写化；
2. **末尾带 NUL**。

而 blob 的比较是**逐字节**的（`FWP_MATCH_EQUAL_CASE_INSENSITIVE` 只支持
`FWP_UNICODE_STRING_TYPE`，不支持 blob）。

#### `FWP_MATCH_PREFIX` 的名字是误导性的，它判的是后缀

这一条直接决定了通配能不能做。微软文档（`ne-fwptypes-fwp_match_type`）原文：

> This flag has a misleading name. It tests whether the value **ends with** the condition value,
> i.e. it the suffix, not the prefix. The types **FWP_BYTE_BLOB_TYPE** (when it contains a string)
> and FWP_UNICODE_STRING_TYPE support this match type.

于是通配里最常见的那种写法有了**精确等价**的表达：

```text
*\chrome.exe   ⟺   「路径以 \chrome.exe 结尾」
```

而且它是**原生**的：新增的程序照样命中，不需要预先知道系统里有哪些程序。

> MinGW 的 `fwptypes.h` 里 `FWP_MATCH_TYPE` 到 `FWP_MATCH_NOT_EQUAL = 10` 就结束了
> （`FWP_MATCH_TYPE_MAX` 还是过时的 11），没有 `FWP_MATCH_PREFIX` / `NOT_PREFIX`。
> 与层 GUID 那次一样，只能把数值写进代码，出处写在常量旁边。

#### 两个必须做对、做错却不报错的细节

| 细节 | 做错的后果 | 实测证据 |
| --- | --- | --- |
| 后缀值**必须带结尾 NUL** | 一条都命中不了，而过滤器照样加得进去 | `\connector.exe`（不带 NUL）三份程序全 `CONNECTED`；带上 NUL 后三份全 `FAILED` |
| 字面量**必须小写化** | 同上 | 全大写的 `\CONNECTOR.EXE` 一份都没拦住；小写化之后连磁盘上写作 `Connector.exe` 的那些也一并命中 |

第二条值得单独说：**小写化让大小写问题消失了**。用户写 `*\Chrome.exe` 还是
`*\chrome.exe` 都能命中，因为比较的两边都被小写化过。反过来（不小写化）则是本项目最怕的
失败方式 —— 规则看起来下发了、实际一条都不封。

#### 只支持能精确表达的写法，其余当场报错

`*字面量`（开头一个 `*`、其余全是字面量）之外都不支持，而且**不能**用「多个条件拼」来凑：

| 写法 | 为什么不行 |
| --- | --- |
| `C:\Tools\*` | 是「前缀」语义，而系统给的是后缀比较 |
| `C:\a\*.exe` | 是「前缀 ∧ 后缀」，同一个字段上放两个条件语义是「或」，拼出来会**比规则宽** |
| `*ch?me.exe` | `?` 要求「这一位是任意一个字符」，后缀比较表达不出来 |
| `*a*b.exe` | 两个 `*` 中间夹字面量，同样表达不出来 |
| `*` | 那不是通配，是「任意程序」，应当写全匹配条件 |

全部返回 `ErrorCode::NotSupported`，说明里给出该改写什么（目录、精确、或全匹配）。
「前缀 ∧ 后缀」那种最危险：拼出来的结果比用户要的宽，而宽的方向正是最难发现的方向。

#### 通配那部分的演练读数

`tmp/drill-s2.11-12.cpp`（走真实引擎，需提权）里的通配部分：

| 断言 | 结果 |
| --- | --- |
| 下发 `proc wildcard = *connector.exe`（出站）→ 条数 2（IPv4/IPv6 各一条，后缀比较与地址族无关） | 通过 |
| `a` / `ab` / `other` / `Case`（磁盘名写作 `Connector.exe`）/ `a\new` / `a\sub\deep` 六份全被拦住 | 通过 |
| 撤销后 `a` 立刻恢复 | 通过 |
| `C:\Tools\*.exe` 被拒绝，错误码 `NotSupported`，且**一条过滤器都不留** | 通过 |

### 3.12 实施 S2.12 时的实测：程序域目录匹配

#### 目录 = 应用标识上的一段字典序区间

文档里 `FWP_MATCH_RANGE` 属于「可排序类型」，而**可排序类型包括 `FWP_BYTE_BLOB_TYPE`**。
于是「某目录下的全部程序」可以表达成：

```text
[ 目录前缀 , 目录前缀的末位码元加一 )
```

这样写出来的是**原生**的一整片，不是一张快照。这正是 S2.12 验收口径
（「目录内新增可执行文件按预期生效」）想要的形状：以后放进这个目录的程序自动覆盖，
不必枚举目录内容，也不必挂目录监视去重下发。

#### 上界不能随手写 —— 三组对照

区间是 `[下界, 上界)`，上界取「下界末位加一」。上界写错会怎样，实测过三种：

| 上界取法 | 结果 | 说明 |
| --- | --- | --- |
| 等于下界 | **加不上**：`FWP_E_INVALID_RANGE`（`0x80320020`） | 系统自己会拒绝退化的区间，不会静默收下 |
| 目录名末位加一（`a` → `b`） | `a` 被拦，**`ab` 被误伤** | 区间变成 `[..\a\, ..\b\)`，比自己大的邻居全被圈进来 |
| **末尾分隔符加一**（`a\` → `a]`） | `a` 被拦，`ab` 与 `other` 不受影响 | 正确解 |

关键在**前缀必须以分隔符结尾**：`..\a\` 与 `..\ab\` 在分隔符那一字节上就分开了
（`\` = 0x5C < `b` = 0x62），所以邻居落在区间外。
而如果前缀停在目录名上（`..\a`），上界就成了 `..\b`，`ab` 恰好落在里面。
用户写目录时带不带尾分隔符都合法（存储层刻意不改写用户写的路径），所以**由平台层补**。

#### 目录前缀从哪来

`FwpmGetAppIdFromFileName0` **不接受目录路径**（实测：带尾分隔符给 `ERROR_PATH_NOT_FOUND`、
不带给 `ERROR_ACCESS_DENIED`）。两条可行的取法都实测过：

| 取法 | 结果 |
| --- | --- |
| 句柄 + `GetFinalPathNameByHandleW(VOLUME_NAME_NT)`，再小写化 | 六个目标的矩阵与正确解一致 |
| 在目录里建临时空文件，用 `FwpmGetAppIdFromFileName0` 问，再截到目录 | 与上一条**字节完全一致**，矩阵也一致 |

实现选了第一种：不往用户的目录里写东西。代价是拿到的是卷上记录的大小写，需要自己小写化，
而且解析的是连接点 / 符号链接**之后**的形态。

#### 取反：补集是两段区间

`dir` 取反的补集是「比下界小」与「比上界大」两段。同字段多条件的语义是「或」，
两段拼起来正好是补集，所以一个取反的目录条件会变成**两个** WFP 条件
（这也是为什么 `AppPathMatch` 不能让平台层「一个条件进、一个条件出」）。
两段的界是自造的：下界一个 U+0000 码元，上界八个 U+FFFF 码元。

#### 目录那部分的演练读数

| 断言 | 结果 |
| --- | --- |
| 下发 `proc dir = …\a`（出站）→ 条数 2（IPv4/IPv6 各一条，每条一个区间条件） | 通过 |
| `a` / `a\new` / `a\sub\deep` 被拦；`ab` / `other` / `Case` **不受影响** | 通过 |
| ⭐ **规则不动**，往 `a\later` 新放一个程序 → 它被拦住，且期间的过滤器条数没变（2 → 2） | 通过 |
| 撤销后 `a` 与 `a\later` 都恢复 | 通过 |
| `dir` + 取反：`a` 这一族放行，`ab` / `other` / `Case` 全被拦 | 通过 |

#### 如实记下的缺口

| 缺口 | 说明 |
| --- | --- |
| UNC / 网络路径上的行为未实测 | 句柄取法给的是 `\device\mup\...` 这类形态，而进程的应用标识在那种路径上是不是同一个形态，没有实测过 |
| `dir` 要求目录在**下发时**存在 | 打不开就报错并给出错误码，不猜一个前缀出来 |
| 目录语义是「整棵子树」 | 区间是前缀比较，所以子目录里的程序也算。这是刻意的（封游戏目录时通常要连子目录一起），但要在界面上说清 |

## 5 阶段验收

九项验收里已有八项实测通过（除第 3 条外全部），逐条对照状态：

| # | 验收项 | 状态 | 证据 |
| --- | --- | --- | --- |
| 1 | 可对指定进程封 IPv4 与 IPv6 的出站与入站，TCP 与 UDP 均有效 | **已实测** | 出站见 3.5、入站见 3.6，四个组合分开计数；「指定进程」由 3.5 的程序条件对照组证明 |
| 2 | 可按远端端口、本地端口与网段精确限定范围 | **已实测** | 见 3.7：远端端口（含区间与多值）在出站上验，本地端口在入站上验，网段含 IPv6 与混族；每一组都带「不误伤」的对照组 |
| 3 | 匹配条件支持任意条件取反，且取反后的实际语义与「人话翻译」一致 | 部分 | 求补与拒绝空补集已有单元测试（S2.4）；「人话翻译」属 S5.6，尚无实物 |
| 4 | 空条件规则被拒绝保存，要表达「全部」必须显式写出全匹配条件 | **已实测** | 仓储入库前跑 `validateRule`，空条件当场拒绝且一条不写（`tests/rule_store_test.cpp`）；校验与拒绝从 S2.1 起就有单元测试 |
| 5 | IPv4 已建立连接能被立即中断，且不会立刻重连成功 | **已实测** | 见 3.8：连接从系统连接表里消失（send 报 10054），且重连被已生效的规则拦住；反例（先断后封会留一个重连窗口）也跑了出来 |
| 6 | 规则撤销后立即恢复，且无残留过滤器 | **已实测** | 出站 31–1031 ms 恢复、入站 15 秒窗口内恢复；每次演练收尾都是「无自家过滤器残留」（3.5、3.6、3.7、3.8） |
| 7 | 重启后规则自动重建，过期规则不再生效 | **已实测** | 见 3.9：跨两个进程，新进程清理残留后按库重建，重建之后真实连接确实被封住；过期规则不下发、巡检后停用 |
| 8 | 连续增删同一规则一百次后，过滤器总数回到初始值 | **已实测** | S2.4 的演练，增删 100 次后总数回到 0 |
| 9 | 未知的匹配域或匹配方式会让该规则被拒绝加载并报错，而不是被宽松解释 | **已实测** | 入库前与**读出来**两道都校验；测试里手工塞一行 `domain = "nonsense"`，`list()` 直接失败并指出是哪一条 |

第 1 条里有两点要说清楚：

1. **IPv6 是在链路本地链路上验的**，不是公网 IPv6。本机没有任何 IPv6 出口，
   这一点不必掩盖：被验证的是「V6 层上的过滤器确实参与判定并且拦住了流量」，
   在公网 IPv6 环境下的行为应当相同（同样的层、同样的条件、同样的权重），但那是推断。
2. **「封住了」在 TCP 上的表现是超时而不是报错**，所以界面文案不能写「连接会被立刻拒绝」。
   详见 3.5。

整条链路可以用一条命令复现（需提权）：`tmp/verify-s2.ps1` 把上面的演练逐个跑一遍、
核对过滤器条数与落点层，并确认每次收尾都没有残留（见 3.10）。
需要手机当外部发起方的两项默认跳过，加 `-WithPeer` 才跑。
程序域的通配与目录由 `tmp/drill-s2.11-12.cpp` 单独验（需先跑 `tmp/prepare-appid-probe.ps1`
布置六份只有路径不同的连接器），结论见 3.11 与 3.12。

## 6 风险与对策

| 风险 | 对策 |
| --- | --- |
| 条件构造错误导致封禁范围过大 | 展开器必须可确定性输出：条件的**形状**由 `tests/filter_plan_test.cpp` 锁死，落点层与条数由 S2.10 的脚本对着系统核对（3.10），不靠目测 |
| 取反条件让规则变宽而用户没察觉 | 规则必须渲染成一句中文，宽条件要被显式标记 |
| 通配写宽了命中意料之外的程序 | 通配只支持「开头一个 `*`、其余全是字面量」的写法（3.11），所以「前缀 + 后缀」那类拼出来的宽语义根本表达不出来；写法过宽的（`*`、`*.exe`）由 S2.1 的风险分级标成高风险，下发前二次确认 |
| 断连后对端立刻重连 | 已落地：「先封后断」在 `core/ban_action.{h,cpp}` 里只有一处定义，有单元测试锁住顺序，实演练也把反例跑了出来（3.8） |
| 地址族或过滤层选错 | 每个能力点都要求 IPv4 与 IPv6 各测一次，不合并验收 |
| 路径转换在特殊卷上失败 | 强制覆盖三类路径，见 S2.3 的验收标准 |
