# 阶段三 观测能力

## 1 目标与范围

把「谁连了谁、传了多少」变成可查询的记录：连接枚举、TCP 与 UDP 流量统计、
记录去重与聚合、批量落库与保留期、按需降频。

本阶段**不做封禁**，也不做界面。它与阶段二使用完全不同的数据源，因此可以并行推进。

## 2 前置条件

| 项 | 状态 |
| --- | --- |
| 阶段一完成 | 接口已冻结，数据库子系统可用 |
| 统计路线 | 见 [architecture.md](../architecture.md) 第 5.1 节 |
| 两个待实测点 | 扩展统计对老连接的有效性、事件是否含进程标识 |
| 平台相关实现 | 枚举与统计经 `IConnMonitor`、`ITrafficStats`、`ISessionMonitor` |

### 3.1 实施 S3.1 时的实测：连接枚举

数据源只有两个**公开**接口，各自的边界都是硬的：

| 关注点 | 实测结论 |
| --- | --- |
| TCP 四元组与进程 | `GetExtendedTcpTable(TCP_TABLE_OWNER_PID_ALL)`，v4 与 v6 各一次，给出四元组、状态与 PID |
| UDP 对端 | **公开 API 里没有**：`MIB_UDPROW_OWNER_PID` 只有本地地址、本地端口、PID |
| UDP 方向 | 于是也判不出来 —— 方向取决于对端是谁，而对端恰恰不知道 |

UDP 那两条是实测出来的：造一个只 bind 的套接字与一个 **已 connect** 的套接字，
两者在端点表里**完全同形**，能读的字段只有那三个。

`netstat` 能打出已 connect 的对方地址，靠的不是公开 API（`objdump -p netstat.exe`）：

```text
DLL Name: IPHLPAPI.DLL
  219  InternalGetUdpTable2
  204  InternalGetTcp6Table2
DLL Name: NSI.dll
    1  NsiAllocateAndGetTable
```

这几个都是**未公开导出**：SDK 头没有、MinGW 头没有，Wine / ReactOS / SystemInformer
的源码里也搜不到。那条路也试过一遍，**五种候选调用形状各放一个进程**（猜错会直接崩，
所以要能分辨「崩了」与「没生效」），结论是不用：

- MinGW 的 `iphlpapi.h` 里有 `AllocateAndGetUdpExTableFromStack` 的原型，
  但 **`iphlpapi.dll` 并不导出它** —— 静态链接的进程在启动时就
  `STATUS_ENTRYPOINT_NOT_FOUND`（`0xC0000139`）；
- 五种形状里四种直接访问违例；
- 唯一不崩的那一种确实给出了含自有套接字的表（本地地址、端口、PID 分别在偏移
  12272、12276、12280），但**对端看不到，整块结构也无法证实**：
  `HeapSize` 给 18156 字节、行数 96，除不尽任何整数行宽。

**决定：不用它。** 理由不是「未公开所以不许用」，而是**它没法被证实**：
布局靠反推、对端拿不到，将来某个版本改了布局就会产出一份
**看着合理的错对端** —— 这正是本项目最怕的错误方向。
于是 UDP 行如实标注为「对端未知、方向未知」，真实对端留给 S3.4 的事件源 ——
那里有完整四元组，而且自带方向。

方向的判据是**推断**出来的，且实测过：

| 判据 | 依据 |
| --- | --- |
| 本地端口落在「本机处于 LISTEN 的端口集合」里 ⇒ 入站 | `accept()` 出来的套接字，本地端口就是监听端口 |
| 否则 ⇒ 出站 | 本机主动发起用临时端口，而该端口不可能同时也是别人正在监听的端口 |

实测：本地 5502 是监听口的那条判为入站、本地 5503 是临时口的那条判为出站，
与构造时一致。**刻意只按端口比、不按地址比** —— 监听套接字常绑在 `0.0.0.0`，
而被接受的连接本地地址是具体网卡地址，按地址比会把入站全判成出站。
已知会判错的场景只有 `SO_REUSEADDR` 端口共享那一类，数量级极小，且只影响显示。

排除的三类行（口径写死在这里，验收就按它对照）：

| 排除的行 | 理由 |
| --- | --- |
| `LISTEN` 状态 | 那是「绑定了端口」，不是连接 |
| `PID = 0` | 系统已不归属任何进程。实测本机 447 条 `TIME_WAIT` 全是这种情况，且 PID=0 只出现在这个状态 |
| 端口为 0 | 构造不出一条连接 |

与系统工具逐条对照（实测读数）：

| 项 | 我们 | netstat | 扣掉时间偏斜后的差异 |
| --- | --- | --- | --- |
| TCP（四元组 + PID） | 147 | 145 | 0 |
| UDP（本地端点 + PID） | 100（唯一键） | 100（唯一键） | 0 |

v4 与 v6 都在清单里（当次 60 行属于 v6）。netstat 的 UDP 行里有 **5 条带真对端** ——
那正是我们如实标为「未知」的那部分，数字要报出来，不能假装不存在。

过程里有三件事值得单独记：

1. ⚠️ **`netstat -p tcp` 只给 IPv4**，IPv6 要用 `-p tcpv6` / `-p udpv6`。
   漏掉它会把整批 IPv6 行记成「系统工具看不到、而我们看得到」。
2. ⚠️ **对照对象是活机器**：同一个四元组会在两次取样之间被别的进程重建
   （实测 `10.92.110.108:1024 → 4.145.79.81:443` 一会儿属于 PID 6712、
   一会儿属于另一个进程）。所以每轮取三次样（我们 → netstat → 我们），
   凡是在自己两次之间就变过的行算时间偏斜 ——
   「机器抖了一下」与「功能没生效」必须分得开，这一条在 S2.7 上吃过亏。
3. ⚠️ **进程标识解析依赖提权**：同一次快照里解不出可执行文件的条数，
   未提权 **98/292**、提权 **6/292**（剩下的 6 条是本机解不出来的系统进程）。
   解不出时留空、**不编名字**，界面据此显示「读不到程序信息」。
   所以 `ProcessEnumeration` 能力位的语义是「这个平台提供这项能力」，
   不是「每一行都解得出来」—— 解不出的行照样在清单里，只是没有程序名。

验收口径因此可以收紧到不含糊：**清单完整、方向按上述判据、UDP 如实标未知**。

## 5 阶段验收

1. 连接清单与系统工具对照一致，且同时覆盖 IPv4 与 IPv6（**S3.1 已实测**：见 3.1，
   TCP 147/145、UDP 唯一键两边都是 100，扣掉时间偏斜后差异为 0；v4 与 v6 均在清单里）
2. TCP 流量数字与持续传输的增量相符
3. UDP 流量的可行性有明确实测结论，落地方式与该结论一致
4. 记录表在长时间运行下不无界增长
5. 无界面时可观测占用接近零
6. 两种来源的口径差异已记录，并明确以哪个为准

## 6 风险与对策

| 风险 | 对策 |
| --- | --- |
| 扩展统计对老连接可能拿不到累计值 | 先实测；若确认不可用，则在连接首次发现时立即启用，并对更早的连接标注为「自启用起计数」 |
| 事件可能不含进程标识 | S3.3 必须先给结论；降级方案为只统计流数与地址，字节数标注为不可用 |
| 事件洪泛导致占用升高 | 订阅时使用关键字与级别过滤，避免全量事件进入用户态 |
| 记录写入放大 | 批量事务与保留期同属 S3.6，一次做完，不留到后期 |
