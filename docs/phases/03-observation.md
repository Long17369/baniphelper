# 阶段三 观测能力

## 1 目标与范围

把「谁连了谁、传了多少」变成可查询的记录：连接枚举、TCP 与 UDP 流量统计、
记录去重与聚合、批量落库与保留期、按需降频。

本阶段**不做封禁**，也不做界面。它与阶段二使用完全不同的数据源，因此可以并行推进。

### 3.1 实施 S3.1 时的实测：连接枚举

数据源只有两个**公开**接口，各自的边界都是硬的：

| 关注点 | 实测结论 |
| --- | --- |
| TCP 四元组与进程 | `GetExtendedTcpTable(TCP_TABLE_OWNER_PID_ALL)`，v4 与 v6 各一次，给出四元组、状态与 PID |
| UDP 对端 | **公开 API 里没有**：`MIB_UDPROW_OWNER_PID` 只有本地地址、本地端口、PID |
| UDP 方向 | 于是也判不出来 —— 方向取决于对端是谁，而对端恰恰不知道 |

UDP 那两条是实测出来的：造一个只 bind 的套接字与一个 **已 connect** 的套接字，
两者在端点表里**完全同形**，能读的字段只有那三个。

`netstat` 能打出已 connect 的对方地址，靠的不是公开 API（`objdump -p netstat.exe`）：

```text
DLL Name: IPHLPAPI.DLL
  219  InternalGetUdpTable2
  204  InternalGetTcp6Table2
DLL Name: NSI.dll
    1  NsiAllocateAndGetTable
```

这几个都是**未公开导出**：SDK 头没有、MinGW 头没有，Wine / ReactOS / SystemInformer
的源码里也搜不到。那条路也试过一遍，**五种候选调用形状各放一个进程**（猜错会直接崩，
所以要能分辨「崩了」与「没生效」），结论是不用：

- MinGW 的 `iphlpapi.h` 里有 `AllocateAndGetUdpExTableFromStack` 的原型，
  但 **`iphlpapi.dll` 并不导出它** —— 静态链接的进程在启动时就
  `STATUS_ENTRYPOINT_NOT_FOUND`（`0xC0000139`）；
- 五种形状里四种直接访问违例；
- 唯一不崩的那一种确实给出了含自有套接字的表（本地地址、端口、PID 分别在偏移
  12272、12276、12280），但**对端看不到，整块结构也无法证实**：
  `HeapSize` 给 18156 字节、行数 96，除不尽任何整数行宽。

**决定：不用它。** 理由不是「未公开所以不许用」，而是**它没法被证实**：
布局靠反推、对端拿不到，将来某个版本改了布局就会产出一份
**看着合理的错对端** —— 这正是本项目最怕的错误方向。
于是 UDP 行如实标注为「对端未知、方向未知」，真实对端留给 S3.4 的事件源 ——
那里有完整四元组，而且自带方向。

方向的判据是**推断**出来的，且实测过：

| 判据 | 依据 |
| --- | --- |
| 本地端口落在「本机处于 LISTEN 的端口集合」里 ⇒ 入站 | `accept()` 出来的套接字，本地端口就是监听端口 |
| 否则 ⇒ 出站 | 本机主动发起用临时端口，而该端口不可能同时也是别人正在监听的端口 |

实测：本地 5502 是监听口的那条判为入站、本地 5503 是临时口的那条判为出站，
与构造时一致。**刻意只按端口比、不按地址比** —— 监听套接字常绑在 `0.0.0.0`，
而被接受的连接本地地址是具体网卡地址，按地址比会把入站全判成出站。
已知会判错的场景只有 `SO_REUSEADDR` 端口共享那一类，数量级极小，且只影响显示。

排除的三类行（口径写死在这里，验收就按它对照）：

| 排除的行 | 理由 |
| --- | --- |
| `LISTEN` 状态 | 那是「绑定了端口」，不是连接 |
| `PID = 0` | 系统已不归属任何进程。实测本机 447 条 `TIME_WAIT` 全是这种情况，且 PID=0 只出现在这个状态 |
| 端口为 0 | 构造不出一条连接 |

与系统工具逐条对照（实测读数）：

| 项 | 我们 | netstat | 扣掉时间偏斜后的差异 |
| --- | --- | --- | --- |
| TCP（四元组 + PID） | 147 | 145 | 0 |
| UDP（本地端点 + PID） | 100（唯一键） | 100（唯一键） | 0 |

v4 与 v6 都在清单里（当次 60 行属于 v6）。netstat 的 UDP 行里有 **5 条带真对端** ——
那正是我们如实标为「未知」的那部分，数字要报出来，不能假装不存在。

过程里有三件事值得单独记：

1. ⚠️ **`netstat -p tcp` 只给 IPv4**，IPv6 要用 `-p tcpv6` / `-p udpv6`。
   漏掉它会把整批 IPv6 行记成「系统工具看不到、而我们看得到」。
2. ⚠️ **对照对象是活机器**：同一个四元组会在两次取样之间被别的进程重建
   （实测 `10.92.110.108:1024 → 4.145.79.81:443` 一会儿属于 PID 6712、
   一会儿属于另一个进程）。所以每轮取三次样（我们 → netstat → 我们），
   凡是在自己两次之间就变过的行算时间偏斜 ——
   「机器抖了一下」与「功能没生效」必须分得开，这一条在 S2.7 上吃过亏。
3. ⚠️ **进程标识解析依赖提权**：同一次快照里解不出可执行文件的条数，
   未提权 **98/292**、提权 **6/292**（剩下的 6 条是本机解不出来的系统进程）。
   解不出时留空、**不编名字**，界面据此显示「读不到程序信息」。
   所以 `ProcessEnumeration` 能力位的语义是「这个平台提供这项能力」，
   不是「每一行都解得出来」—— 解不出的行照样在清单里，只是没有程序名。

验收口径因此可以收紧到不含糊：**清单完整、方向按上述判据、UDP 如实标未知**。

### 3.2 实施 S3.3 时的实测：事件里到底有没有进程标识

第 5 节把这一点列为「在验证之前代码里不允许做假设、界面也不允许显示猜测值」。
结论是**有**，而且判据是运行时模板加行为对照，不是推测：

| 事实 | 依据 |
| --- | --- |
| UDP 事件带进程标识 | 事件模板里**第 1 个字段的名字就叫 `PID`** |
| 它的值就是流量归属 | 自己发一个 29 字节的 UDP 包，事件的 `PID` 等于本进程、`size` 等于 29 |
| 事件头里的进程号**不能用** | 同一条流量的 `EventHeader.ProcessId` 在 4（system）与真实 PID 之间跳，也有 0 的 |

⚠️ **`wevtutil gp` 看不到这个字段**：它的消息串只从 `%2` 起显示
（`UDPv4: %2 bytes transmitted from %4:%6 to %3:%5`），`%1` 是存在的但不展示。
完整字段清单只能在运行时问 `TdhGetEventInformation` 拿。
「消息串里没提」不等于「事件里没有」—— 这一条如果按前者下结论，
就会把「UDP 不能归属到程序」写进设计，而那是错的。

UDP 的字段与顺序（v4：事件 42 发出 / 43 收到；v6：58 / 59）：

| 字段 | 含义 | 编码 |
| --- | --- | --- |
| `PID` | 归属进程 | 32 位 |
| `size` | 本次数据报的字节数 | 32 位 |
| `saddr` / `daddr` | 源/目的地址 | v4 是四字节网络序，v6 是十六字节 |
| `sport` / `dport` | 源/目的端口 | 十六位**网络序**（要 `ntohs`） |
| `seqnum` / `connid` | 本机实测恒为 0 | —— |

同 provider 的 TCP 事件号：10 发出 / 11 收到 / 12 尝试连接 / 13 连接关闭 / 14 重传 /
15 已建立 / 16 重连 / 17 尝试失败 / 18 TCPv6 发出。

三点影响：

1. **S3.4 原先写的降级方案不需要了**（原文：「若不含进程标识则降级为按流统计不统计字节」）——
   UDP 的字节数可以归属到程序；
2. **归属必须读载荷的 `PID`，不能读事件头** —— 读错会把流量安静地算到系统进程头上，
   而且不会报错，正是本项目最怕的那种错法；
3. ✅ **loopback 的 UDP 也在采集范围内**（原以为不会）→ 自环与内网流量同样能统计，
   而 S2.5/S2.6 已经记过「本机自连被系统豁免」，观测侧与封禁侧的结论**不一样**，不能互推。

实现按**字段名**取值，不依赖类型常量表（本机工具链里没有 `TDH_INTYPE_*` 那一族，
而照 SDK 手抄一份数值表的后果是把字段解释成错的值，比拿不到值更糟）。

### 3.3 实施 S3.3 的事件模块：朝向、过滤与合成

3.2 定的是「事件里有没有归属进程」，这一步定的是**怎么把事件变成一条连接**。
三件事都不能靠推：`saddr` 指谁、订阅要不要收数据事件、失败尝试算不算一条连接。

#### 朝向：`saddr` 在两种协议下指的不是同一端

两端端口都已知的回环连接是唯一能分清这件事的构造，实测结果如下：

| 事件 | `saddr:sport` 是谁 | 判据 |
| --- | --- | --- |
| TCP 全部（10 发 / 11 收 / 12 尝试 / 13 关闭 / 15 接受 / 18 代复制） | **恒为本端** | 收包事件（11）的 `sport` 是**接收方**端口 10359，而那个包实际从 10360 发出 |
| UDP 发出（42 / 58） | 发包方，即本端 | `sport` 就是发送套接字的端口 |
| UDP 收到（43 / 59） | 发包方，即**对端** | 收包事件的 `sport` 是 49254（发送方的端口），不是接收套接字的 49253 |

也就是说：**TCP 的载荷是逐连接的朝向，UDP 的载荷是逐报文的朝向**。
把 UDP 按 TCP 那样解释，会让所有接收方向的对端都变成自己 —— 不报错、不崩溃，
只是记录全错，属于本项目最怕的错法。两个方向都各有断言守着。

关闭与失败事件里判不出方向：回环里两端各自产生一条关闭事件，都把自己放在 `saddr`，
所以「谁先关的」事件本身没说。这类事件的方向如实标 `Unknown`，
**不挑一个填上** —— 方向不是连接键的一部分，不影响匹配。

#### 订阅只订生命周期事件，过滤在内核侧

同一个提供程序也带着**每个报文**一条的数据事件（收发、重传、代复制、UDP 收发），
而连接发现只需要四种：尝试、重连、接受、关闭（另加 IPv4 的「尝试失败」）。
订阅时按事件号过滤，让这些事件**根本不进用户态**：

| 项 | 实测（5 秒，同一台机器） |
| --- | --- |
| 只订「连接尝试」（事件 12） | 15 条 |
| 只订数据事件（10/11/14/18/26/27/30/34/42/43/49/58/59） | 326 条 |

差 20 倍，这就是「过滤真的在内核侧生效」的判据：若过滤被忽略，两次都会拿到全量事件。
这件事直接关系到「空闲时零占用」：只订生命周期时约为四十条每秒，
而全量是它的二十倍以上。

事件号在两族下**不是同一批**（12/15/13 与 28/31/29），所以两种地址族各自验过一遍 ——
「IPv4 对了就外推到 IPv6」在本项目里不成立。另外，TCPv6 **没有**「连接尝试失败」事件
（提供程序清单里 33 号缺失），这一点记在下面「缺口」里。

#### 合成：尝试算「出现」，失败与关闭算「消失」

| 事件 | 合成结果 |
| --- | --- |
| 连接尝试 / 重连尝试（12/16，28/32） | `Appeared`，方向出站 |
| 接受连接（15/31） | `Appeared`，方向入站 |
| 连接关闭（13/29）、尝试失败（17） | `Disappeared` |
| 数据类事件 | **不产生连接事件** |

把「尝试」当成出现是有意的：对封禁工具来说「某个程序正在往外连」本身就是要展示的信息，
而出站方向的连接**只有这一个事件**（实测：本机主动连出去时只有 12 与 13，
「接受」事件只在被动一侧产生）。代价是一次失败的尝试会先出现再消失 —— 如实发生，不掩盖，
而且 IPv4 有失败事件收尾，不会留下幽灵连接。

同一个连接只上报一次出现：重复的尝试与重连一律压掉（接口契约要求「不重复上报」，
否则记录表会被重连风暴打爆）。关闭事件**不设门口**：漏掉一条关闭会在记录里
留下一条永远不消失的连接，比多报一条严重得多。闸门有容量上限并有溢出计数，
溢出时丢最早的记录 —— 那一条连接下次出现会多报一次出现，代价已知且不会无界增长。

#### 起会话的权限检查发生在第二处

⚠️ **实测：未提权时 `StartTraceW` 会成功**，失败发生在 `EnableTraceEx2`
（返回 5，访问被拒）—— 权限检查是在**启用系统提供程序**那一步做的。
只查第一处的实现会把「请以管理员身份运行」写成一句没人看得懂的「平台错误」。
两处都要映射成「权限不足」，并且要有非空的中文说明；契约测试对
「声明了能力却报不支持」和「未提权却报的不是权限不足」各有一条断言。

#### 落地的判据与缺口

行为演练（四组可控流量，27 项断言全过）：IPv4 与 IPv6 的成功连接各产生一对
`Appeared`（客户端口一侧为出站、监听口一侧为入站）、关闭后各产生 `Disappeared`；
连一个关闭的端口产生 `Appeared` 紧跟 `Disappeared`；退订之后不再收到任何事件。
单元测试锁的是判据本身：两种朝向约定、订阅清单里不许混进数据事件、去重与溢出的规则。

如实记下的三个缺口：

| 缺口 | 说明 |
| --- | --- |
| UDP 的数据报事件**没有**进这条通道 | 它们是逐报文的，当 `Appeared` 上报会把记录表打爆。UDP 行仍然只从快照来，逐包数据留给 S3.4 |
| 失败尝试在 **IPv6** 侧没有收尾事件 | 提供程序缺「TCPv6 尝试失败」，所以一次失败的 v6 尝试会留下一条记录，等后续关闭事件或保留期清理 |
| 被过滤器拦下的尝试是否仍产生事件 | 未实测。本工具封禁时流量是被 WFP 拦的，那一步之后内核还发不发「连接尝试」事件，直接决定界面上会不会出现一批幽灵连接 |

「关闭事件滞后」也值得记一笔：它比出现事件慢得多（演练里第一条关闭事件超过 3 秒才到），
判据的等待窗口给短了会读成「没上报」。

## 5 阶段验收

1. 连接清单与系统工具对照一致，且同时覆盖 IPv4 与 IPv6（**S3.1 已实测**：见 3.1，
   TCP 147/145、UDP 唯一键两边都是 100，扣掉时间偏斜后差异为 0；v4 与 v6 均在清单里）
2. TCP 流量数字与持续传输的增量相符
3. UDP 流量的可行性有明确实测结论，落地方式与该结论一致（**S3.3 已实测**：见 3.2，
   事件带 `PID` 字段，因此**不需要**降级为「只统计流数」；事件模块已落地，见 3.3）
4. 记录表在长时间运行下不无界增长
5. 无界面时可观测占用接近零
6. 两种来源的口径差异已记录，并明确以哪个为准

## 6 风险与对策

| 风险 | 对策 |
| --- | --- |
| 扩展统计对老连接可能拿不到累计值 | 先实测；若确认不可用，则在连接首次发现时立即启用，并对更早的连接标注为「自启用起计数」 |
| 事件可能不含进程标识 | S3.3 必须先给结论；降级方案为只统计流数与地址，字节数标注为不可用 |
| 事件洪泛导致占用升高 | 订阅时使用关键字与级别过滤，避免全量事件进入用户态 |
| 记录写入放大 | 批量事务与保留期同属 S3.6，一次做完，不留到后期 |
